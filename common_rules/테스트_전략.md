# 테스트 전략

- 테스트 코드도 `코드_규칙.md`를 따른다.
- 언어 · 도구에 매이지 않게 썼다. Python 프로젝트의 명령 · 설정은 맨 끝 "부록: Python 예"에 있다.

## 1. 테스트 층

| 층 | 위치 | 확인하는 것 | 기본 실행 |
|---|---|---|---|
| 정적: lint | 린터 | 코드 오류 · 스타일, import 순서 | 커밋 전 0건 |
| 정적: 타입 | 정적 타입 검사 도구 | 타입 오류, import 순환 | 커밋 전 0건 |
| 정적: 계층 | import 규칙 검사 도구 | import 방향, 순환 | 커밋 전 모든 계약 통과. 계약이 지켜지는지 확인하는 테스트도 둔다 |
| 단위 | 테스트 러너, `tests/unit/` | 함수 · 모듈 동작, 실패 경로 | 들어간다 |
| 런타임: 입력 경계 | 엄격 모드 검증 모델 등 운영 코드 | 환경변수 · 설정 파일 · API 요청 · 저장 키 검증 | 단위 테스트에서 거부 경우를 확인한다 |
| 통합 | 테스트 러너, `tests/integration/`. 가짜 외부 응답 + 임시 폴더, 실제 브라우저 · 하위 프로세스 | API 요청부터 결과 파일까지, 실제 브라우저 동작, 쓰는 도중 강제 종료 | 들어간다. 성공한 전체 처리 e2e 테스트는 끝에 결과 파일 검사 도우미 하나로 파일 · 크기 · 해시 · 형식 · 상태 파일을 확인한다 |
| 외부 연동 | `tests/live/` | 실제 외부 서비스가 바뀌었는지 | 빠진다. 경로를 지정할 때만 실행한다. 외부 서비스마다 목록 조회와 첫 항목 하나를 받아 형식을 확인한다. 자격증명은 메인 저장소 `.env`에서 읽고, 환경변수가 없거나 비면 skip하며 사유에 빠진 환경변수 이름을 쓴다 |
| 스모크 | `tests/smoke/` | 새 컨테이너 이미지가 기동하고 대표 처리 하나를 끝내는지 | 빠진다. 빌드 → 컨테이너 실행 → 헬스 체크 → 대표 처리 1회 → 결과 파일 검사. 컨테이너 실행 도구가 없으면 실패한다. 기록은 `<실행 기록 폴더>/<날짜>_smoke_<대상>/` |

- 두 층 이상이 같이 쓰는 도우미(결과 행 검사, 상태 파일 읽기, 결과 파일 검사 등)는 `tests/` 바로 아래에 둔다. 이유: 테스트 러너가 `tests/`를 import 경로에 넣으면 모든 층에서 같은 이름으로 import된다.

## 2. TDD

- 새 코드 · 버그 수정은 실패하는 테스트를 먼저 쓰고(RED), 통과시킨다(GREEN).
- 여러 입력을 같은 기준으로 확인하면 표(매개변수화 테스트)로 쓴다.
- 인수 조건은 spec에 적고 사용자가 spec과 함께 승인한다.
- plan의 Task마다 test 세션이 설계서 · plan의 인터페이스와 인수 조건을 보고 테스트를 먼저 쓰고 실패(RED)를 확인한다. review 세션이 그 테스트를 본 뒤 coding 세션이 구현한다. 구현 중인 코드를 보고 테스트를 맞추지 않는다.
- test 세션은 진행 중인 Task의 테스트만 쓴다. 다음 Task의 테스트는 앞 Task를 커밋한 뒤에 쓴다. 이유: 아직 없는 모듈을 import하는 테스트 파일은 테스트 수집 단계에서 실패하고, 같은 worktree에 커밋하지 않은 채 있으면 앞 Task의 커밋에 섞일 수 있다.
- 관측된 경우만 테스트한다. 합성 입력만으로 새 처리를 정당화하지 않는다.

## 3. 실행 시점

| 시점 | 실행하는 것 | 하는 세션 |
|---|---|---|
| 커밋 전마다 | 테스트 기본 실행(단위 + 통합 전체), import 규칙 검사, 린터, 정적 타입 검사, 포매터 검사(포매터를 쓰는 프로젝트) | test 세션 |
| PR 전 | 외부 연동 테스트(외부 연동 모듈을 고쳤을 때), 스모크 테스트(이미지 · 의존성을 고쳤을 때) | 사용자가 직접 |

- 커밋 전에 단위와 통합을 모두 실행한다. 이유: 기본 실행 전체가 1분 안쪽(실측)이면 층을 나눠 고르는 것은 커밋마다 단계만 늘린다.
- coding 세션이 수정 중일 때는 실행하지 않는다. coding 세션이 "구현 끝"을 알린 뒤 실행한다. 이유: 중간 상태에서 나온 실패는 의미가 없다.

## 4. 실행 환경

- worktree는 가상 환경이 따로다. 처음 한 번 의존성을 설치한다.
- worktree에서 메인 저장소의 가상 환경을 쓰면 메인 저장소의 소스(기본 브랜치)를 import한다. 그 worktree의 가상 환경으로 실행한다. 다른 저장소의 소스를 가리키는 가상 환경 때문에 모듈을 찾지 못하면, 활성화된 가상 환경 변수를 지우고 의존성을 다시 설치한다.
- 설정 객체가 읽는 환경변수는 공통 fixture가 테스트마다 모두 지운다. 이유: 개발자 셸의 값이 테스트 결과를 바꾸지 않게. 테스트 안에서 설정이 필요하면 그 테스트에서 환경변수를 다시 넣는다.
- 저장소가 추적하는 설정 파일을 서버가 읽으면, 서버를 직접 실행할 때 그 파일의 절대경로를 환경변수로 준다. 외부 연동 테스트는 환경변수가 없으면 저장소 루트의 파일을 읽는다.

## 5. 실제 외부 서비스 실행 결과

- 실제 실행 결과를 `<실행 기록 폴더>/<날짜>_<티켓>_<대상>/`에 남길 때는 요약 파일(결과 행 · 작업 기록), 서버 로그, 쓴 설정 파일, 상태 파일만 남긴다.
- 작업이 끝나고 결과를 확인한 뒤 내려받거나 만든 큰 파일(PDF · ZIP 등)을 지운다. 이유: 전체 처리 한 번이 12GB를 남긴 적이 있다.
- 지운 뒤 폴더 구성을 보고한다.

## 부록: Python 예

| 역할 | Python |
|---|---|
| 린터 | `uv run ruff check src tests` |
| 정적 타입 검사 | `uv run pyright` |
| 포매터 검사 | `uv run ruff format --check src tests` |
| import 규칙 검사 | `uv run lint-imports`(모두 `KEPT`), 계약 테스트 `tests/unit/test_import_rules.py` |
| 테스트 러너 | pytest. 기본 실행 `uv run pytest`, 외부 연동 `uv run pytest tests/live`, 스모크 `uv run pytest tests/smoke` |
| 기본 실행 범위 | `pyproject.toml` `[tool.pytest.ini_options]` `testpaths = ["tests/unit", "tests/integration"]` |
| 매개변수화 테스트 | `@pytest.mark.parametrize` |
| 엄격 모드 검증 모델 | pydantic `strict` |
| 실제 브라우저 | Playwright Chromium |
| 공통 fixture 위치 | `tests/conftest.py`(autouse fixture). `tests/conftest.py`가 있으면 pytest가 `tests/`를 import 경로에 넣는다 |
| 테스트 안 환경변수 | `monkeypatch.setenv` |
| 의존성 설치 | `uv sync`. `uv run`은 실행 전에 `.venv`를 `uv.lock`에 맞춘다 |
| 모듈을 찾지 못할 때 | `ModuleNotFoundError: <패키지>` → `env -u VIRTUAL_ENV uv sync`. `--no-sync`로 실행할 때도 같다 |
