# 코드 규칙

- 코드를 쓸 때 따르는 기준이다. 테스트 코드도 이 규칙을 따른다.
- 언어 · 도구에 매이지 않게 썼다. Python 프로젝트의 구체적인 이름 · 설정은 맨 끝 "부록: Python 예"에 있다.

## 1. 처리 범위

- 원본 데이터, 조사, 실측, 스모크 · 실제 외부 서비스 실행에서 본 경우만 처리한다. 합성 입력으로만 재현한 경우는 관측으로 치지 않는다.
- 동작을 바꾸지 않고 로그만 남기는 감지는 처리로 보지 않는다(예: 목록 안 중복 키를 ERROR 로그로만 기록하는 것). 건너뛰기 · 거부 · 값 보정은 처리다.
- 구조상 꼭 필요해 보이는 방어 코드는 넣지 말고 사용자에게 묻는다. 남긴다면 그 코드를 빼고 실행해 보는 등 조사로 필요를 증명하고, 상한 · 임계값은 실측 근거가 있어야 한다.
- 근거가 불분명한 처리는 빼고 테스트와 재현을 실행해 본다. 실패하지 않으면 지운다.
- 처리하지 않은 경우가 실제로 생기면 알 수 있게, 무엇을 봤는지 적은 경고 로그를 둔다.
- 리뷰어나 내가 가정한 경우를 처리하자고 하면 관측이 있는지 먼저 보고, 없으면 후속 작업으로 적는다.
- 예외: 애플리케이션으로서 필요한 안전 장치(무한 반복 상한, 빈 결과를 성공으로 저장하지 않기, 끊긴 연결 다시 열기 등)는 관측이 없어도 둔다. 설계 문서에 이유와 "실측 없음"을 적고 사용자 승인 뒤 구현한다. 이유: 운영 환경의 네트워크 · 외부 서비스는 개발 환경에서 관측하지 못한 방식으로 실패할 수 있다. 속도 · 분류만 바꾸는 처리는 이 예외가 아니다.
- 사용하지 않는 필드는 검사하지 않는다. 항목 하나에만 해당하는 필드는 목록을 받는 단계가 아니라 그 항목을 처리하는 단계에서 검사한다. 이유: 목록 단계에서 실패하면 목록 전체가 실패로 기록된다.
- 복사(깊은 복사, 맵 · 리스트 복사)는 원본이나 복사본을 제자리에서 바꾸는 코드가 있을 때만 한다.
- 맵(dict) 읽기는 자리에 따라 고른다.
  - 키가 반드시 있어야 하는 자리(바로 앞에서 확인했거나 방금 넣은 키)는 키가 없으면 예외가 나는 읽기를 쓴다. 이유: 없으면 버그이므로 예외로 드러나야 한다.
  - 키가 없는 것이 정상인 자리는 없으면 빈 값을 반환하는 읽기를 쓰고 바로 빈 값을 처리한다. 이유: 전부 빈 값 반환이면 버그가 빈 값으로 숨고, 전부 예외 읽기면 정상인 경우에도 예외가 난다.
  - 같은 상황에는 같은 방식을 쓴다.

## 2. 계층과 import

- 계층 순서는 import 규칙 검사 도구의 계약으로 강제한다. 계층 순서는 프로젝트마다 한 줄 그림으로 이 절 첫머리에 적는다. 예:

  ```
  진입점 → HTTP 계층 | 실행 엔진 → 업무 계층 → 상태 · 외부 연동 | 출력
         → 공통 모델 · 오류 → 범용 유틸 | 설정 | 저장소
  ```

- 위 계층만 아래 계층을 import한다. `|`로 묶은 모듈끼리는 서로 import하지 않는다.
- 순환 import를 만들지 않는다. 타입 검사 때만 실행되는 import나 함수 안 import로 순환을 피하지 않고, 정의 위치를 옮겨 없앤다.
  - 계층 계약은 나열한 모듈 사이의 순환만 검사하고, 한 패키지 안 모듈끼리의 순환은 검사하지 않을 수 있다. 패키지 안 순환은 따로 계약을 둬서 검사하고, 맨 위 import · 함수 안 import · 타입 검사용 import를 모두 검사하는지 복사본에 순환을 넣어 확인한다.
- 패키지 안 순환 계약이 위반으로 나오면 coding 세션은 고치지 않고 멈춘다. review 세션이 순환 경로, 없앨 후보 import, 정의를 옮길 곳(어느 모듈인지, 계층 계약을 지키는지)을 정리해 main에 보내고, main이 사용자에게 물어 정한다. 이유: 정의를 옮기는 것은 모듈 배치 변경이고, 다른 계층으로 옮기면 사용자 결정이 필요하다.
  - 검사 도구가 보여 주는 "끊을 import"는 후보 하나일 뿐이라, 없앨 import는 순환 경로를 보고 정한다.
- 꼭 필요하지 않으면 새 계층 · 폴더를 만들지 않는다.
- **HTTP API가 있는 프로젝트: HTTP 계층은 바로 아래 업무 계층을 import해도 된다.** 조건:
  1. HTTP 계층은 업무 계층만 거친다. 저장소 · 실행 엔진 · 외부 연동 · 출력 모듈을 직접 쓰지 않는다.
  2. 업무 계층과 그 아래는 HTTP를 모른다. 상태 코드 · 헤더를 정하지 않고 거부 · 실패 사유만 예외로 알린다. 상태 코드는 HTTP 계층의 표 하나(사유 코드 → 상태 코드)에서 정한다.
  3. HTTP 계층에는 판단 로직을 두지 않는다. 접수할지 거부할지는 업무 계층이 정한다.
- 범용 유틸(로깅 · 마스킹 · 시각)은 도메인 모듈(오류 정의 포함)을 import하지 않는다. 코드 안에 도메인 이름이 있는 것(로그 문맥 필드 이름 등)은 괜찮다.
- 같은 인터페이스의 구현이 여럿일 때(예: 외부 서비스마다 연동 모듈 하나)
  - 구현 공통 모듈은 오류 정의를 알아도 되지만, 개별 구현 · 실행 엔진 · 업무 계층은 import하지 않는다. 새 구현 모듈은 공통 모듈 계약의 금지 목록에 추가한다.
  - 개별 구현과 구체 저장소 구현은 진입점(조립하는 모듈)만 import한다. 다른 곳은 인터페이스(추상 클래스)를 쓴다. 개별 구현끼리 서로 import하지 않는다. import 규칙 계약으로 검사하고, 새 구현을 더하면 계약 목록에도 추가한다.
  - 두 개 이상의 구현이 같은 동작을 하면(이름이 달라도) 공통 모듈로 옮긴다. 한 곳에서만 쓰는 헬퍼는 그 구현에 둔다. 옮기는 커밋은 따로 만든다. 이유: 사용자가 공통 모듈 티켓으로 옮길 수 있게.
  - 새 구현을 쓸 때 private 헬퍼를 만들기 전에 공통 모듈과 다른 구현에서 같은 동작을 먼저 찾는다.
  - 모듈 이름은 다루는 형식(`pdf`)보다 하는 일(`stream`)로 짓는다.
- 모듈을 다른 계층으로 옮기는 것은 사용자에게 묻는다. 같은 계층 안의 파일 배치는 직접 정한다.
- 저장소 키 · 파일 이름은 경로 모듈 하나의 함수 · 상수로만 만든다. 다른 모듈에서 문자열 조합으로 경로를 쓰지 않는다.
- 요청마다 똑같이 하는 처리(로그 문맥, 액세스 로그)는 미들웨어 한 곳에 둔다.

## 3. 자료구조와 메소드

| 값의 성격 | 쓰는 것 |
|---|---|
| 정해진 값 중 하나(상태 · 모드 · 결과 · 코드 · 소스 이름) | 문자열 값을 가진 열거형. 그 값을 담는 모델 옆에 둔다. 구현 하나에만 있는 값은 그 구현에 둔다 |
| 구현이 여럿인 인터페이스 | 추상 클래스 + 추상 메서드 |
| 주입 함수 | 함수 타입 별칭 |
| 테스트용 가짜 객체 | 우리 인터페이스는 그 추상 클래스를 상속. 라이브러리의 구체 클래스를 대신하면 타입 단언(cast)으로 넘긴다 |
| 묶은 값, 바뀌지 않음 | 불변 값 객체. 바꿀 때는 일부 필드만 바꾼 새 객체를 만든다 |
| 한 대상의 바뀌는 상태 | 가변 값 객체 하나. 같은 키로 맵 여러 개에 나눠 담지 않는다 |
| 튜플로 쓸 일이 있는 레코드(정렬 키, 언패킹) | 이름 붙은 튜플 |
| 밖에서 들어오는 입력(설정 파일, API 요청, 외부 서비스 응답) | 엄격 모드 검증 모델. 외부 응답 모델은 응답 출처마다 모듈 하나에 둔다 |
| 서로 묶어 넘길 일이 없는 고정값 | 모듈 상수. 상수를 모으려고 값 객체 인스턴스를 만들지 않는다 |

- 구조적 타이핑 인터페이스(메서드 구성만 맞으면 받는 방식, duck typing)는 쓰지 않는다. 목적에 맞는 클래스를 쓴다: 구현이 여럿인 인터페이스는 추상 클래스, 값 · 상태는 값 객체, 밖에서 들어오는 입력은 검증 모델, 그 밖은 일반 클래스. 이유: 들어오는 데이터의 타입이 정해져 있으므로 메서드 구성만 맞추는 방식이 필요 없다.
- 문자열 리터럴(`"failed"`)로 상태를 비교 · 대입하지 않는다. 런타임에 만드는 값(`UNHANDLED_<예외 클래스>`)은 열거형 밖에 둔다.
- 반환 튜플은 요소 2개까지. 3개 이상이면 먼저 메서드가 일을 너무 많이 하는지 보고, 그래도 필요하면 값 객체를 쓴다.
- 다른 필드로 계산되는 값은 계산 속성(property)으로 둔다. 클래스 상태를 쓰지 않는 정적 메서드는 모듈 private 함수로 둔다.
- 같은 일을 두 곳에서 정하지 않는다. 같은 단계의 거부 검사는 한 함수에, 같은 값은 한 곳에 둔다. 한 함수에서 빈 값 반환과 예외를 섞지 않는다.
- 상태 · 플래그 이름은 값이 참인 기간과 맞춘다(끝난 뒤에도 참인 -ing 플래그 금지). 코드 · 상수 이름이 가리키는 범위는 실제 판단 조건과 같게 한다.
- 공개 함수 이름이 다른 모듈의 공개 함수와 같으면 입력 · 반환 형태와 하는 일도 같아야 한다. 다르면 이름을 다르게 짓는다. 예: 시각 모듈의 `iso`가 시각 객체를 ISO 8601 문자열로 바꾼다면, 날짜 문자열이 `YYYY-MM-DD` 또는 `YYYY-MM`인지 검사해 적힌 정밀도 그대로 반환하는 함수는 하는 일이 달라 `parse_iso`로 짓는다. 이유: 같은 이름을 보고 같은 일을 한다고 판단해 잘못 쓰게 된다.
- 다른 경우를 위한 판정 함수를 빌려 쓰면(재시도 처리가 증분 처리용 판정 함수를 부르는 식) 그 함수의 입력 전제가 이 경우에도 맞는지 확인한다. 맞지 않으면 따로 둔다.
- 구조화된 외부 응답(JSON 등)은 검증 모델로 검증한다. 이유: 일반 값 객체는 타입 · 빈 값을 검증하지 않는데, 응답 구조가 바뀌면 경고와 파싱 실패로 알아야 한다. 검증 모델로 표현하기 어려운 응답(HTML 등)은 파싱 도우미 함수로 읽는다.

## 4. 예외 · 로그

- 운영 코드에 `assert`와 단언 실패 예외를 직접 발생시키는 코드를 쓰지 않는다. 실패할 수 없는 조건이면 구조로 해결하고(값을 인자로 넘기기, 확정된 분기 안에서 처리), 일어날 수 있는 조건이면 조건문과 커스텀 예외를 쓴다.
- 로거는 모듈마다 모듈 이름으로 만든다. 핸들러 · 포맷 · 레벨 설정은 로깅 설정 함수 하나를 진입점에서 한 번만 호출한다.
- 로그 인자는 포맷 문자열과 인자를 따로 전달한다(`logger.info("저장 key=%s", key)`). 문자열 보간으로 미리 만든 문장을 전달하지 않는다. 예외는 트레이스백을 함께 기록하는 로그 함수로 기록한다. 표준 출력에 직접 쓰지 않는다.
- 마스킹은 로깅 설정에서 한 번에 한다. 호출하는 쪽이 매번 마스킹하지 않는다.
- 레벨: DEBUG 개발용 상세, INFO 정상 흐름, WARNING 계속 진행할 수 있는 이상, ERROR 그 작업의 실패.
- 로그 문구는 짧은 명사구 + key=value로 쓴다. 문장(~했다)으로 쓰지 않는다. 예: `처리 대상 결정 mode=…`, `요청 거부 code=…`

## 5. 형식과 정적 검사

- 정적 검사 설정(린터, 정적 타입 검사 도구)은 프로젝트 설정 파일 하나에 둔다.
  - 린터는 그 버전의 기본 규칙에 프로젝트가 필요한 규칙만 더한다. 더하는 규칙의 예: 문자열 보간 로그, 표준 출력 직접 쓰기, 예외 처리 안에서 원인 예외를 연결하지 않고 새 예외 발생.
  - 줄 길이 기준을 정해 설정에 적는다.
  - 두 도구 모두 버전을 정확히 고정한다. 이유: 새 버전은 규칙 · 검사를 더한다. 버전을 올리면 설정 파일이 바뀌는 그 커밋에서 새 지적이 함께 드러난다.
- 커밋 전마다 린터와 정적 타입 검사 도구가 0건이어야 한다. 새 지적은 그 지적을 만든 브랜치에서 고친다. 이유: 지적을 0건으로 만든 뒤에는 새 지적이 그것을 만든 변경에 속한다.
- 지적을 고치지 않고 무시할 때는 지적된 줄 끝에 규칙 이름을 적은 무시 주석을 쓰고, 그 줄 위에 이유 주석(개조식)을 쓴다. 규칙 이름 없이 모든 지적을 무시하는 주석은 쓰지 않는다. 예: 일부러 모든 예외를 처리하는 줄의 "넓은 예외 처리" 규칙 무시.
- 타입 검사 도구가 빈 값 가능성을 지적하지만 타입으로 증명할 수 없는 곳은 타입 단언(cast) · 타입 표기로 고치고, 라이브러리 타입이 허용하지 않으면 이유 주석을 단 무시 주석을 쓴다. `assert`나 새 "빈 값이면 예외 발생" 분기를 넣지 않는다. 이유: 운영 코드에는 `assert`를 쓰지 않고, 새 예외 분기는 관측되지 않은 경우의 처리가 된다.
- 새 프로젝트는 첫 커밋부터 포매터를 쓰고 커밋 전 검사에 넣는다. 포매터 없이 쓴 코드가 있는 저장소에서는 전체에 실행하지 않는다. 이유: 형식만 바뀐 줄이 변경 diff에 섞이는 비용은 포매터 없이 쓴 코드가 있을 때만 생긴다.
  - 포매터 없이 쓴 코드가 있는 저장소에서는 주변 코드처럼 정한 줄 길이에 맞춰 손으로 줄바꿈한다. 형식이 맞지 않아 실제 문제(리뷰에 형식만 바뀐 줄이 섞임, 충돌)가 생기면 사용자에게 알리고, 한 번만 하는 재정렬을 별도 변경으로 제안한다.
- import를 옮기거나 이름을 바꿀 때 그 import 블록 안의 알파벳 순서를 유지한다. 린터의 import 순서 규칙이 검사한다.
- 의존성은 패키지 · 잠금 파일 관리 도구로 설치되어 있다. 새 패키지는 추가하지 않는다(필요하면 사용자에게 묻는다). 동작 확인은 그 도구로 프로젝트 환경의 인터프리터를 실행해서 한다.

## 부록: Python 예

Python 3.12 · uv · ruff · pyright · import-linter · pydantic 프로젝트에서 위 규칙에 대응하는 이름이다.

| 규칙의 말 | Python |
|---|---|
| 키가 없으면 예외가 나는 읽기 · 빈 값 반환 읽기 | `d[k]` · `d.get(k)` |
| 복사 | `copy.deepcopy`, `dict(x)`, `list(x)` |
| 타입 검사 때만 실행되는 import | `if TYPE_CHECKING:` 아래 import |
| 문자열 값을 가진 열거형 | `enum.StrEnum` |
| 추상 클래스 + 추상 메서드 | `abc.ABC` + `@abstractmethod` |
| 함수 타입 별칭 | `Login = Callable[[Page], Awaitable[None]]` |
| 타입 단언(cast) | `typing.cast` |
| 불변 값 객체 · 일부만 바꾼 새 객체 | `@dataclass(frozen=True)` · `dataclasses.replace` |
| 가변 값 객체 | `@dataclass` |
| 이름 붙은 튜플 | `typing.NamedTuple` |
| 엄격 모드 검증 모델 | pydantic `BaseModel`, `model_config = ConfigDict(strict=True)` |
| 구조적 타이핑 인터페이스 | `typing.Protocol` |
| 계산 속성 · 정적 메서드 | `@property` · `@staticmethod` |
| 단언 실패 예외 | `raise AssertionError` |
| 모듈 이름 로거 | `logger = logging.getLogger(__name__)` |
| 트레이스백을 함께 기록 | `logger.exception(...)` |
| 표준 출력 직접 쓰기 | `print` |

- import 규칙 검사: import-linter(`lint-imports`), 설정은 `pyproject.toml` `[tool.importlinter]`.
  - 계층 계약 `type = "layers"`: 나열한 모듈 사이 순환만 검사한다. 한 패키지 안(`pkg.a` ↔ `pkg.b`) 순환은 검사하지 않는다.
  - 패키지 안 순환 계약 `type = "acyclic_siblings"`, `ancestors = ["<최상위 패키지>"]`: 맨 위 import, 함수 안 import, `TYPE_CHECKING` 아래 import를 모두 검사한다.
  - 위반 출력 예: `No cycles are allowed in pkg.run.` 아래 `- .history -> .manager (1 import)`. 결과는 `KEPT`(통과) · `BROKEN`(위반).
  - 최상위 패키지를 일반 패키지로 두면 새 폴더마다 `__init__.py`가 필요하다.
- 린터 ruff, 정적 타입 검사 도구 pyright. `pyproject.toml` 예:

  ```toml
  [dependency-groups]
  dev = ["ruff==0.17.3", "pyright==1.1.414", "import-linter>=2.16"]

  [tool.ruff]
  line-length = 100
  target-version = "py312"

  [tool.ruff.lint]
  # G004 f-string 로그, T20 print, B904 except 안 raise에 from 없음
  extend-select = ["G004", "T20", "B904"]

  [tool.pyright]
  typeCheckingMode = "standard"
  reportImportCycles = true
  include = ["src", "tests"]
  ```

  - ruff 기본 규칙에는 줄 길이 초과(E501)가 없어 100열은 검사하지 않는다.
  - import 순서 규칙: I001.
- 커밋 전 명령: `uv run ruff check src tests`, `uv run pyright`.
- 무시 주석: `# noqa: BLE001`(일부러 모든 예외를 처리하는 `except Exception`), `# pyright: ignore[reportOptionalMemberAccess]`.
- 포매터: `ruff format`. 커밋 전 검사는 `uv run ruff format --check src tests`.
- 의존성 설치 `uv sync`, 동작 확인 `uv run python -c ...`.
