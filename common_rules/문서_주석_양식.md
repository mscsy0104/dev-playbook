# 문서 · 주석 양식

- 코드 주석, docstring, 로그 문구, 응답 메시지, 설계서, 조사 · 질의응답 문서에 모두 적용한다.

## 1. 공통 문장 규칙

- 일어나는 일을 그대로 쓴다. 무엇을 읽고, 쓰고, 지우고, 거부하고, 반환하는지 쓴다. 추상적이고 근거 없는 표현, 구어 · 개발 은어를 쓰지 않는다. 뜻이 분명한 비유나 넓은 범위를 묶는 용어는 맞는 자리에서 쓴다.
- 가리키는 대상이 드러나게 쓴다. "마감 파일", "옛 내용", "바깥 취소" 대신 "`orders.csv` · 상태 파일", "서버 종료로 작업 태스크가 취소되는 것"처럼 쓴다.
- 용어로 줄이기보다 짧은 문장으로 쓴다. 용어 없이 뜻이 통하면 용어를 쓰지 않는다. 새 용어는 처음 한 번 정의한다.
- 상황을 단정하지 않고 조건으로 쓴다: "로그인이 거부되는 경우,", "내용이 그대로라면,".
- 이유를 함께 쓴다. 길면 "이유: …"로 짧게 붙인다.
- 단위는 대상에 보통 쓰는 것만: 문서 · 행은 건, 글자는 자, 파일 · 코드는 개. 프로젝트 용어집에 정의한 낱말은 정의한 대상에만 쓴다.
- 다른 곳을 보라는 안내("아래 표", "위와 같다", "(4절)", "설계서 5 4절")를 쓰지 않는다. 필요한 내용은 그 자리에 쓴다.
  - 예외: 읽을 파일 경로 자체가 내용인 것(문서 지도), 작업 위치 지시("`<리뷰 기준 파일>` 끝에 추가", "README 용어집에 정의", "CHANGELOG에 기록").
  - 위치 안내를 최신 내용으로 바꿀 곳이 있으면 목록을 먼저 보여 주고 묻는다.
- 규칙 · 전략 문서에 "초안", "나중에 정한다", "확인 후 정한다" 같은 미정 상태를 적지 않는다. 정할 것이 남으면 그 세션에서 사용자에게 물어 정하고, 정해진 내용을 쓴다.
- 따라가기 어려운 곁가지 상황은 뺀다.
- 사용자의 요청 · 코멘트에 흐린 말이 있으면 결과물에는 분명한 말로 쓴다. 뜻이 분명하지 않으면 묻는다.

예외(남기는 말):
- 뜻이 딱 맞아 일부러 쓴 말. 예: 용어집에 단계 이름으로 정의한 "판정"(목록과 저장된 상태를 비교해 처리 대상을 정하는 단계).
- 비유지만 뜻이 분명한 말. 예: "덮어쓰는 것을 막는다".
- 개발에서 정해진 뜻으로 쓰는 말. 예: 응답 · 스트림을 닫는다, 연결이 끊긴다.
- 예외인지 애매하면 사용자에게 한 번 묻는다.

고치는 대상은 추상적이고 근거 없는 표현이다. 뜻이 분명한 비유나 넓은 범위를 묶는 용어가 맞는 자리에서는 그 말을 쓴다.

표현을 고치면 이력을 `<표현 변경 기록 폴더>`에 표로 남긴다: `| 위치 | 원래 표현 | 결정(바꿈 · 남김) | 바꾼 표현 | 근거 |`. 남긴 것도 근거와 함께 쓴다.

## 2. 코드 주석 · docstring · 로그

- 주석 · docstring에서 "여기" · "이곳" 같은 가리킴말 대신 모듈 · 함수 · 클래스 · 상수 이름을 쓴다. 이유: 코드가 옮겨지면 가리키는 곳이 달라지고, 읽는 사람이 어디를 말하는지 찾아야 한다.
- 코드 이름(함수 · 변수 · 상수)은 짧고 명확하게 짓는다. 개발 용어를 써도 된다(`sweep_orphans`). 주석 · 로그는 풀어 쓰고, 개발 용어와 도메인 용어는 `<용어집 파일>` 용어집에 정의한다.
- 주석의 용어와 코드 이름을 맞춘다. 용어를 바꾸면 같은 뜻의 함수 · 변수 · 테스트 이름도 함께 바꾼다.
- **코드 주석은 개조식으로 쓴다.** 첫 줄은 요약, 더할 내용은 `# - ` 불렛. "~다."로 끝내지 않고 명사형("~함", "~있음", "~사용")으로 끝낸다. 예: `# 분류: 응답의 documentType 필드 사용(화면 표시 "Doc Type")`. 새로 쓰거나 고치는 주석에 적용하고, 기존 주석은 후속 작업으로 맞춘다.
- 주석은 필요한 내용만 짧고 구체적으로 쓴다. 코드로 보이는 내용은 다시 쓰지 않는다. 코드만으로 의도가 안 보이는 선택(예: `max(…, 0)`)에는 짧은 주석을 단다.
- **docstring은 한 줄 요약이 기본이다.**
  - 요약 줄도 개조식으로 쓴다. "~다."로 끝내지 않고 명사형으로 끝낸다. 예: `"""값 하나 또는 여러 값을 `|`로 이은 문자열"""`. 새로 쓰거나 고치는 docstring에 적용하고, 기존 docstring은 그대로 둔다.
  - 인자 · 반환값 섹션을 쓰지 않는다. 타입 표기로 충분하다.
  - 코드로 알 수 없는 것(예외 조건, 부작용, 전제)이 있을 때만 빈 줄 뒤에 개조식 불렛으로 더한다. 이유는 불렛 안에 "이유: …"로, 순서가 있는 절차는 번호 목록으로.
  - 리팩터링 중에는 기존 docstring을 새로 쓰지 않는다. 옮긴 코드는 docstring도 그대로 둔다.
- 설계서 출처("설계서 4 6-1절")를 적지 않는다. 내용을 직접 쓴다.
- **로그 문구는 짧은 명사구 + key=value**로 쓴다. 문장("~했다")으로 쓰지 않는다. 예: `처리 대상 결정 mode=…`, `결과 파일 · 상태 파일 쓰기 실패`, `요청 거부 code=…`.
- **주석 · docstring은 규칙대로 쓰고, 내용이 모호할 때만 묻는다.** 내용은 추상적이지 않게(어디서 무엇이 일어나고 그 뒤 무엇을 하는지), 표현은 개조식으로 쓴다. 이 규칙을 따른 문구는 승인 표를 따로 받지 않고 리뷰가 규칙 준수를 확인한다. 무엇을 쓸지(동작 · 이유 · 전제)가 코드와 설계로 정해지지 않을 때만 main을 거쳐 사용자에게 묻는다. 사용자의 해석이 코드 동작과 다르면 받아쓰지 않고 다른 점을 짚는다.

## 3. 설계서 (`<설계서 폴더>`)

- 설계가 바뀌면 작업본을 직접 고치고 `CHANGELOG.md`에 항목을 쓴다. 이유: `<문서 폴더>`를 git으로 추적하지 않으면 CHANGELOG가 유일한 변경 기록이다.
- 문서 머리말:
  ```
  # 설계서 N — 제목

  > 변경은 같은 폴더의 `CHANGELOG.md`에 기록한다.

  - 최근 수정일: YYYY-MM-DD
  - 수정 사항: 이번 수정 (이전: 지난 수정 …)
  - 대상: 이 문서가 다루는 범위
  ```
- CHANGELOG 항목: `### 날짜 · 문서 번호 · 무엇을` 제목, 첫 줄에 `확정: 사용자(날짜).`와 ADR 경로(`<결정 기록 폴더>/<티켓>.md`), 그 아래 문서 · 절별 변경 불렛. 최신 항목을 위에 쓴다. 결정 근거는 ADR에 쓰고 CHANGELOG에는 다시 쓰지 않는다.
- 본문에 출처(티켓 번호, 사용자 결정 날짜, 다른 문서 경로)를 쓰지 않는다. 실측값과 실측 날짜는 쓴다. 결정 근거는 ADR(`<결정 기록 폴더>/<티켓>.md`)에 쓴다.
- 설계에만 있고 실측 근거가 없는 항목은 지운다. 위험 대비로 필요해 보이면 사용자에게 묻는다. 설계 담당자의 요청에서 온 항목(rollback 등)은 요구 사항이라 따로 결정을 받는다.
- 다른 장을 가리키는 할 일 목록은 설계서에 두지 않고 `<정리 문서 폴더>`로 옮긴다.
- 표로 쓸 수 있으면 표로 쓴다. 과한 설명은 줄인다.

## 5. 결정 기록(ADR)

- 티켓마다 `<결정 기록 폴더>/<티켓>.md` 하나를 쓴다. 결정 근거의 원본은 이 문서다. `<진행 상태 파일>`의 티켓 행에는 상태와 ADR 경로만, 설계서 `CHANGELOG.md`에는 문서 변경 목록과 ADR 경로만 쓴다.
- 사용자가 정한 것만 쓴다. 선택지나 이유가 기록으로 남지 않았으면 "기록 없음"으로 쓰고 지어내지 않는다.
- 머리말: 제목 `# <티켓> 결정 기록`, 티켓 내용 한 줄, 브랜치, spec · plan 경로.
- 결정 하나:
  ```
  ## 번호. 결정 제목

  - 날짜: YYYY-MM-DD
  - 배경: 무엇을 정해야 했는지, 그때의 상태
  - 선택지: 검토한 안
  - 고른 것: 정한 내용(이름 · 문구 · 값은 그대로)
  - 이유: 고른 이유
  ```
