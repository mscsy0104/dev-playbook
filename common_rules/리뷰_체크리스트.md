# 리뷰 체크리스트

- review 세션은 코드를 고치지 않고 지적만 한다. 칭찬은 쓰지 않는다. 버그와 규칙 위반을 찾는다.
- 언어 · 도구에 매이지 않게 썼다. Python 프로젝트의 명령 · 패턴은 맨 끝 "부록: Python 예"에 있다.

## 1. 리뷰 대상

- **커밋 전 리뷰**: worktree의 커밋하지 않은 변경 전체.
  - 이미 있던 파일의 변경: `git -C <worktree> diff`
  - 새로 만든 파일: `git -C <worktree> status --porcelain`의 `??` 행. diff에 나오지 않으므로 파일을 직접 읽는다.
- **브랜치 리뷰**: `git diff <base branch>...<branch>`
- **설계 리뷰**: 설계서 · spec · plan 문서. 이 체크리스트의 "설계" 항목과, 일어나는 일을 그대로 쓰는지 · 은어가 없는지 · 위치만 가리키는 문장이 없는지로 본다.

## 2. 확인할 것

지적할 때 해당 항목 번호(예: "체크 B-3")와 파일:줄을 함께 쓴다.

### A. 처리 범위

1. 처리 코드와 테스트의 근거가 실측 · 원본 데이터인가, 합성 데이터인가. 문서 · 주석에 "생길 수 있다", "미리" 같은 말이 붙어 있는가.
2. 검사한 값을 실제로 쓰는가. 같은 검사가 두 번 있는가. 목록 단계에서 항목 하나의 필드를 검사하는가.
3. 복사한 값(깊은 복사, 맵 · 리스트 복사)을 나중에 제자리에서 바꾸는 곳이 있는가. 없으면 복사가 필요 없다.

### B. 계층과 import

1. import 규칙 검사 도구의 계약이 모두 통과하는가(worktree에서는 그 worktree의 가상 환경으로 실행한다). 계약을 새로 더하거나 고쳤으면, 그 계약이 금지하는 import를 하나 넣은 복사본에서 그 계약이 위반으로 나오는지 확인했는가. 이유: 계약이 잘못되어도 통과로 나온다.
2. 함수 안 import나 타입 검사용 import로 순환을 피한 흔적이 있는가.
3. (HTTP API가 있는 프로젝트) HTTP 계층이 저장소 · 실행 엔진 · 외부 연동 · 출력 모듈을 직접 쓰는가. HTTP 계층에 접수 · 거부 판단이 들어갔는가.
4. (HTTP API가 있는 프로젝트) HTTP 계층 밖 모듈에 `409` · `422` · `503` 같은 상태 코드 숫자나 상태 코드 인자가 있는가. 사유 코드마다 HTTP 계층의 사유 코드 → 상태 코드 표에 상태 코드가 있는가.
5. 범용 유틸이 오류 정의나 도메인 모듈을 import하는가. 구현 공통 모듈이 개별 구현 · 실행 엔진 · 업무 계층을 import하는가.
6. 개별 구현이나 구체 저장소 구현을 진입점 밖에서 import하는가. 개별 구현끼리 import하는가. 새 구현이 공통 모듈 계약의 금지 목록에 들어갔는가. 이 항목은 import 규칙 계약으로 검사한다. 새 구현을 더하면 계약 목록에도 추가한다.
7. 두 구현에 같은 동작(이름이 달라도)이 있는가.
8. 경로 모듈 밖에 저장 경로 문자열 조합(`"results/"` · `"/state.json"` 같은 조각)이 있는가.
9. 엔드포인트 · 예외 핸들러에 요청 로그 문맥 설정이나 요청 헤더 로그가 반복되는가.

### C. 자료구조와 메소드

1. 같은 문자열 리터럴을 여러 모듈에서 비교 · 대입하는가. 같은 리터럴 값 목록 타입이 여러 곳에 반복되는가.
2. 요소 3개 이상 튜플 반환, 위치로 꺼내는 튜플이 있는가.
3. 같은 키로 넣고 지우는 맵이 여러 개인가. 지우는 함수가 같은 키 삭제를 여러 번 하는가.
4. 필드 두 개가 같은 정보를 따로 저장하는가. 정적 메서드가 있는가. 상수를 담은 값 객체 인스턴스가 있는가.
5. 호출하는 곳이 하나뿐인 검사 함수, 빈 값 반환과 예외 발생이 섞인 함수, 같은 상수가 두 번 적힌 곳이 있는가.
6. 하던 일이 끝난 뒤에도 참으로 남는 -ing 플래그가 있는가. 이름의 낱말이 다른 열거형에도 있고 범위가 다른가. 공개 함수 이름이 다른 모듈의 공개 함수와 같은데 입력 · 반환 형태나 하는 일이 다른가(예: 시각 모듈의 `iso`는 시각 객체를 문자열로 바꾸고, 날짜 문자열을 검사하는 함수는 하는 일이 달라 `parse_iso`로 짓는다).
7. 판정 함수를 그 함수가 전제한 경우가 아닌 값(다른 처리 방식의 모드 값 등)으로 호출하는가.

### D. 예외 · 로그

1. 운영 코드 안에 `assert`(특히 "빈 값 아님" 단언)나 단언 실패 예외를 직접 발생시키는 곳이 있는가.
2. 모듈 이름으로 만들지 않은 로거, 진입점 밖의 로깅 설정 · 핸들러 추가, 문자열 보간으로 만든 로그 문구, 예외 메시지만 기록해 트레이스백을 버리는 곳, 표준 출력 직접 쓰기가 있는가.
3. 로그 문구가 짧은 명사구 + key=value인가.

### E. 문서 · 주석

1. 다음 낱말을 grep으로 찾는다: 잡는다 · 올린다 · 던진다 · 삼킨다 · 놓는다 · 신호를 켠다 · 막는다 · 막힌다 · 풀린다 · 끊는다 · 끊긴다 · 돈다 · 도는 · 로 본다 · 걸리면 · 걸린 · 넘긴다 · 건드리지 · 가린다 · 맡는다 · 뜬다 · 정리 · 판정 · 연다 · 닫힌다 · 마감 · 돌려준다 · 준다 · 고아 · 본체 · 가장 최근 · 이긴다 · 이때 · 그때 · 휘발 · 몰리면 · 찍는다 · 들고 있다 · 쥐고 있다 · 새는 · 빈 파일 · 오탐 · 미탐 · 한 벌 · 종(개수) · 미처리 · 죽는다 · 죽은 · 소비 · 사슬 · 스택 맨 위 · 없던 일로 · 게이트 · 노이즈 · 미출현 · 분(미처리분 등) · 미시도 · 남긴다 · 남는다 · 부른다 · 낸다 · 버린다 · 거른다 · 걸러낸다 · 전량 · 온다 · 나온다 · 들어온다.
   - 남겨도 되는 것: 용어집에 단계 이름으로 정의한 "판정", "덮어쓰는 것을 막는다", "응답 · 스트림을 닫는다", "연결이 끊긴다".
2. docstring에 인자 · 반환값 섹션, 시그니처를 다시 풀어 쓴 줄이 있는가. 이동만 한 커밋에서 docstring이 바뀌었는가.
3. 주석 용어와 코드 이름이 같은가. 설계서 출처나 다른 절 안내가 있는가. grep: `절` · `장` · `따른다` · `참고`.
4. 새로 쓰거나 고친 주석, docstring의 요약 줄 · 불렛이 개조식인가: "~다."로 끝나지 않고 명사형("~함", "~있음", "~사용")으로 끝나는가. 기준은 `문서_주석_양식.md`의 코드 주석 · docstring 규칙이다. 이유: 리뷰가 낱말 표만 확인하면 "~다."로 끝난 새 주석 · docstring이 통과하고, 주석만 고치는 커밋을 따로 더하게 된다.

### F. 형식 · 테스트

1. 포매터를 커밋 전 검사에 넣은 프로젝트는 포매터 검사가 0건인가. 포매터 없이 쓴 코드가 있는 저장소에서는 자동 포매터로 형식만 바뀐 줄이 섞였는가. 린터(import 순서 규칙 포함)와 정적 타입 검사 도구가 0건인가. 무시 주석에 규칙 이름이 있고, 그 줄 위에 이유 주석이 있는가.
2. 테스트가 바뀐 동작을 확인하는가. 실패 경로 테스트가 있는가.
3. 커밋 전 검사(테스트 전체, import 규칙 검사, 린터, 정적 타입 검사, 포매터 검사(포매터를 쓰는 프로젝트))를 모두 통과했는가: 테스트 통과, import 계약 모두 통과, 린터 · 타입 검사 · 포매터 검사 0건.

### 설계

1. 사용자와 정하지 않은 동작(거부 코드, 상태, 대체 동작, 설정 이름 · 기본값, 예외 경우)이 결정된 것처럼 적혀 있는가.
2. 실측 근거 없이 정한 값(상한, 임계값)이 있는가.
3. 설계서와 코드가 다른 곳이 있는가.

## 3. 결과 보고

- 지적마다: 항목 번호, 파일:줄, 무엇이 문제인지, 실제로 어떤 입력에서 어떻게 잘못되는지.
- 이 목록에 없지만 다른 코드에도 적용할 만한 기준이 나오면 따로 적어 사용자에게 제안한다. 사용자가 동의하면 `<리뷰 기준 파일>` 끝에 새 번호로 추가하고(기준 · 확인할 것 · 출처), 이 체크리스트의 해당 절에 확인할 것을 함께 추가한다. 새 포인트는 리뷰 코멘트가 아니라 다른 코드에도 적용할 기준으로 쓴다.

## 부록: Python 예

| 항목 | Python에서 찾는 것 |
|---|---|
| A-3 복사 | `deepcopy`, `dict(x)`, `list(x)` |
| B-1 import 규칙 검사 | `uv run lint-imports`가 모두 `KEPT`(위반은 `BROKEN`) |
| B-2 순환 회피 흔적 | 함수 안 `import`, `if TYPE_CHECKING:` |
| B-4 상태 코드 인자 | `status_code` · `http_status` 인자 |
| B-8 경로 조합 | `f"results/` · `f"states/` 같은 f-string |
| B-9 요청 로그 반복 | 엔드포인트마다 `request_context` 설정 |
| C-1 리터럴 값 목록 반복 | `Literal["a", "b"]` |
| C-2 튜플 반환 | `tuple[X, Y, Z]` |
| C-3 같은 키 삭제 반복 | `pop`을 여러 번 |
| C-4 정적 메서드 | `@staticmethod` |
| D-1 단언 | `assert x is not None`, `AssertionError` |
| D-2 로거 · 로그 | `getLogger(__name__)`이 아닌 로거, `main.py` 밖 `basicConfig` · `addHandler`, f-string 로그, `logger.error(str(e))`, `print` |
| E-2 docstring 섹션 | `Args:` · `Returns:` |
| F-1 포매터 · 검사 | `uv run ruff format --check src tests` 또는 `ruff format`으로 바뀐 줄, `uv run ruff check src tests`(I001 포함), `uv run pyright`, `# noqa: <규칙>` · `# pyright: ignore[<규칙>]` |
| F-3 커밋 전 검사 | `uv run pytest`, `uv run lint-imports`, `uv run ruff check src tests`, `uv run pyright`, `uv run ruff format --check src tests`(포매터를 쓰는 프로젝트) |
