# 에이전트 운영

- cmux에서 Claude 세션 여러 개를 역할별로 나눠 실행하고, 사용자는 IDE에서 디버깅한다.
- 값 자리표시: `<repo>` 메인 저장소 절대경로, `<티켓>` 티켓 번호, `<branch>` 작업 브랜치, `<base branch>` 브랜치를 만드는 기준 브랜치, `<worktree>` worktree 폴더 이름.
- 의존성 설치 같은 언어별 명령은 맨 끝 "부록: Python 예"에 있다.

## 1. 세션

| 세션 | 작업 폴더 | 모델 · 모드 | 하는 일 | 하지 않는 일 |
|---|---|---|---|---|
| main | 메인 repo | Opus | 사용자와 결정하기, 결정을 `<진행 상태 파일>`에 쓰기, 작업 나눠 주기, git(worktree · 커밋 · push), 티켓의 마지막 커밋 뒤 회고(`<회고 폴더>/<티켓>.md`) 쓰기 | 문서 · 코드 직접 수정(한두 줄 제외) |
| design | 메인 repo | Opus | 설계서 · spec · plan 작성, 질문 목록, 설계에 들어간 설정 변경을 복사본에서 실행해 결과를 spec에 적기 | 코드 수정 |
| concept | 메인 repo | Opus | 이번 티켓에 필요한 개념과 선택지를 읽은 코드를 근거로 설명해 `<개념 문서 폴더>/<티켓>_<주제>.md`에 한국어로 쓴다. 주제마다 파일 하나. design과 동시에 시작하고, 문서를 쓴 뒤 main이 세션을 닫는다 | 코드 · 다른 문서 수정, git 쓰기 명령 |
| review | 메인 repo | Opus | 설계 리뷰, 커밋 전 리뷰 | 코드 · 문서 수정 |
| coding | worktree | Sonnet | `src/` 구현, 커밋 | `tests/` 수정 |
| test | coding과 같은 worktree | Sonnet | `tests/` 작성, 정적 검사 · 테스트 실행 | `src/` 수정, 커밋 |
| docs | 메인 repo | Opus | 문서 수정 전담. 다른 세션이 메시지로 보낸 `<문서 폴더>` 문서 수정, 끝나면 바꾼 파일과 요약을 보낸 세션에 알림 | 코드 수정, git 쓰기 명령 |
| audit | 메인 repo | Opus, 모드 제한 없음. 이유: 결과를 `cmux agent message`(Bash)로 보내야 해서 모드 제한 없이 띄우고, 읽기만 하는 것은 첫 메시지로 정한다 | 대조 · 점검(읽기만) | 파일 수정, git 쓰기 명령 |

- 작업을 맡길 세션이 떠 있지 않으면 사용자를 기다리지 않고 이 표의 구분대로 세션을 만든다(띄우는 명령과 첫 메시지는 "세션 띄우기" 절). 이유: 사용자가 병렬 작업용 세션을 미리 만들어 두지 않는다.
- 이 표의 어느 세션에도 맞지 않는 작업이 생기면 새 세션의 역할(작업 폴더 · 모델 · 모드 · 하는 일 · 하지 않는 일)을 사용자에게 묻는다. 사용자가 동의하면 세션을 만들고 이 표에 행을 추가한다.
- main은 세션을 시작하거나 재개할 때 `에이전트_운영.md`와 `문서_주석_양식.md`를 다시 읽는다. 이유: 다시 읽지 않으면 주석 수정안 승인 절차와 지시 문서 · 세션 이름 형식을 놓친다.
- main이 문서 · 코드를 직접 고치는 예외는 한두 줄뿐이다. 내용이 대화에만 있어도 지시 문서에 옮겨 적어 docs · coding 세션에 맡긴다. 이유: main이 "넘기는 비용이 더 크다"고 보고 예외를 넓혀 직접 고치면, main이 쓴 docstring이 코드 동작과 달라도 리뷰를 거치지 않아 바로 드러나지 않는다.

- worktree 위치: `.claude/worktrees/<티켓>-<slug>`.
- coding과 test를 같은 worktree에 두는 이유: 다른 브랜치에 두면 로컬 merge가 필요하다. 고치는 폴더(`src/` · `tests/`)를 나누고 커밋은 coding 세션만 한다. 이유: 둘 다 커밋하면 git의 `index.lock`이 충돌한다.
- 모델 배치는 판단이 많은 일(design · review)에 큰 모델, 정해진 일(coding · test)에 빠른 모델을 둔 것이다. 두 배치를 비교 측정한 적은 없다.

## 2. 세션 띄우기

```bash
cd <repo>
git worktree add .claude/worktrees/<티켓>-<slug> -b <branch> <base branch>
ln -s ../../../CLAUDE.md .claude/worktrees/<티켓>-<slug>/CLAUDE.md
# 그 worktree에서 의존성 설치(부록)

R=<repo>
W=$R/.claude/worktrees/<티켓>-<slug>
A=$R/<작업 큐 폴더>
cmux new-workspace --name "main"   --cwd $R --command "claude --model opus"
cmux new-workspace --name "design" --cwd $R --command "CAVEMAN_DEFAULT_MODE=caveman claude \"$A/<지시 문서> 를 읽고 따른다\" --model opus"
cmux new-workspace --name "concept" --cwd $R --command "CAVEMAN_DEFAULT_MODE=caveman claude \"$A/<지시 문서> 를 읽고 따른다\" --model opus"
cmux new-workspace --name "review" --cwd $R --command "CAVEMAN_DEFAULT_MODE=caveman claude \"$A/<지시 문서> 를 읽고 따른다\" --model opus"
cmux new-workspace --name "coding" --cwd $W --command "CAVEMAN_DEFAULT_MODE=caveman claude \"$A/<지시 문서> 를 읽고 따른다\" --model sonnet --add-dir $R/<문서 폴더>"
cmux new-workspace --name "test"   --cwd $W --command "CAVEMAN_DEFAULT_MODE=caveman claude \"$A/<지시 문서> 를 읽고 따른다\" --model sonnet --add-dir $R/<문서 폴더>"
cmux new-workspace --name "docs"   --cwd $R --command "CAVEMAN_DEFAULT_MODE=caveman claude \"$A/<지시 문서> 를 읽고 따른다\" --model opus"
cmux new-workspace --name "audit"  --cwd $R --command "CAVEMAN_DEFAULT_MODE=caveman claude \"$A/<지시 문서> 를 읽고 따른다\" --model opus"
```

- 세션 이름은 `--name`으로 `<역할>-<티켓>`을 준다. 세션을 띄우기 전에 이 형식을 확인한다. 이름을 준 워크스페이스는 터미널 제목이 바뀌어도 이름이 유지된다.
- worktree 세션(coding · test)은 `--add-dir $R/<문서 폴더>`를 준다. 이유: `<문서 폴더>`를 gitignore로 두면 worktree 밖에만 있어, 없으면 지시 문서를 읽을 때마다 권한 확인에서 멈춘다.
- 첫 메시지는 옵션보다 앞에 둔다. 이유: `--add-dir`는 디렉토리를 여러 개 받아서, 뒤에 둔 첫 메시지를 디렉토리로 읽는다.
- 띄운 뒤 `cmux read-screen --workspace <ref>`로 작업을 시작했는지 확인한다.

- 세션마다 첫 메시지로 역할과 범위를 알린다.
- 역할 · 작업 지시는 `<작업 큐 폴더>`에 지시 문서로 쓰고("main 중심 작업 큐" 절의 형식), 띄우는 명령의 첫 메시지는 "`<지시 문서 경로>`를 읽고 따른다" 한 줄로 준다. 이유: 긴 지시를 명령에 그대로 넣으면 셸에 입력만 되고 claude가 시작되지 않는다.
  - main: "너는 main 세션이다. 사용자와 결정하고, 결정을 <진행 상태 파일>에 쓰고, 작업을 나눠 다른 세션에 보낸다. git(worktree · 커밋 · push)을 맡는다. 문서 · 코드는 한두 줄 말고는 직접 고치지 않는다."
  - design: "너는 design 세션이다. 설계서 · spec · plan 작성과 질문 목록을 만든다. 코드는 고치지 않는다."
  - concept: "너는 concept 세션이다. 이번 티켓에 필요한 개념과 선택지를 읽은 코드를 근거로 설명해 `<개념 문서 폴더>/<티켓>_<주제>.md`에 한국어로 쓴다. 주제마다 파일 하나. 코드 · 다른 문서는 고치지 않고 git 쓰기 명령은 쓰지 않는다."
  - review: "너는 review 세션이다. 설계 리뷰와 커밋 전 리뷰를 한다. 코드 · 문서는 고치지 않는다."
  - coding: "너는 coding 세션이다. `src/`를 구현하고 커밋한다. `tests/`는 고치지 않는다."
  - test: "너는 test 세션이다. `tests/`를 작성하고 정적 검사 · 테스트를 실행한다. `src/`는 고치지 않고 커밋하지 않는다."
  - docs: "너는 docs 세션이다. 문서 수정만 한다. 작업은 `cmux agent message`로 받고, 끝나면 바꾼 파일과 요약을 보낸 세션에 알린다. 코드는 고치지 않고 git 쓰기 명령은 쓰지 않는다."
  - audit: "너는 audit 세션이다. 대조 · 점검만 하고 파일은 읽기만 한다. 결과는 main에 보낸다. 파일을 고치지 않고 git 쓰기 명령은 쓰지 않는다."
- main 외 세션은 명령 앞에 `CAVEMAN_DEFAULT_MODE=caveman`을 붙여 caveman이 켜진 채로 시작한다. main은 붙이지 않는다.
- main 외 세션은 영어로 작업한다: 채팅 출력, 세션 사이 메시지, 지시 · 결과 문서. 사용자가 읽는 파일(개념 문서 · 회고)과 코드 주석 · docstring · 로그 · 설계서는 원래 언어 규칙(한국어)을 따른다.
- 띄운 뒤 `/memory`로 `CLAUDE.md`가 읽혔는지 확인한다(worktree 세션은 특히).
- worktree를 만든 직후 루트 `CLAUDE.md`의 심볼릭 링크를 worktree에 만든다: `ln -s ../../../CLAUDE.md .claude/worktrees/<worktree>/CLAUDE.md`. 이유: `CLAUDE.md`를 `.git/info/exclude`로 추적하지 않으면 worktree에 없어 세션이 자동으로 읽지 못한다. 링크를 두면 확인 창 없이 자동으로 읽는다. 링크는 `.git/info/exclude` 때문에 git status에 잡히지 않는다. 지시 문서에는 CLAUDE.md를 읽으라고 쓰지 않는다.

## 3. 진행 상태 파일

- 모든 세션은 작업을 시작할 때 `<진행 상태 파일>`를 읽는다. 브랜치 · PR 순서, 미뤄 둔 작업, 임시값, 세션 작업판, 사용자 결정 대기를 이 파일 하나에 둔다. 이유: worktree 세션은 memory를 읽지 못할 수 있고, `<문서 폴더>`가 gitignore 대상이면 worktree에 없다.
- main은 사용자와 정한 내용을 먼저 이 파일(세션 작업판 · 사용자 결정 대기)에 쓰고 작업을 보낸다. 사용자 결정은 고른 값만 적지 않고, 사용자에게 보인 선택지와 고른 이유를 함께 적는다. 이유: ADR을 쓰는 docs 세션은 대화를 보지 못한다. 고른 값만 있으면 docs 세션이 ADR에 선택지 · 이유를 쓰지 못하고, main이 대화 내용을 따로 문서로 옮겨 줘야 한다.
- 각 세션은 작업을 끝내면 세션 작업판의 자기 행(상태 · 결과 파일)을 고친다.

## 4. 작업 흐름

0. **개념 설명**: concept 세션이 design 세션과 동시에 시작해, 이번 작업에 필요한 개념과 선택지를 `<개념 문서 폴더>/<티켓>_<주제>.md`에 쓰고 사용자가 읽는다. 문서를 쓴 뒤 main이 concept 세션을 닫는다.
1. **설계**: design 세션이 질문 목록을 먼저 만든다. 사용자가 답한 뒤 spec · plan을 쓴다. 인수 조건은 spec에 적는다. 설계에 설정 변경(import 규칙 계약, 정적 검사 설정 등)이 들어가면 design 세션이 복사본에 그 설정을 넣어 실행하고 결과를 spec에 적는다. 복사본에서 실행하는 이유: design 세션은 코드를 고치지 않는다. 실행하는 이유: 실행하지 않고 설계한 import 규칙 계약이 정상 구조(HTTP 계층 → 업무 계층 → 저장소)까지 금지한 것이 설계 리뷰에서 실행해 본 뒤에야 드러난 적이 있다.
2. **설계 리뷰 · 승인**: review 세션이 설계 리뷰를 한다. 사용자가 spec(인수 조건 포함)과 plan을 승인한다.
3. **테스트 먼저**: plan의 Task마다 test 세션이 `tests/`에 테스트를 먼저 쓰고 실패(RED)를 확인한다. review 세션이 그 테스트를 본 뒤 coding 세션이 시작한다. 이유: 구현을 보고 테스트를 맞추지 않고, 인수 조건을 테스트로 먼저 고정한다. test 세션은 진행 중인 Task의 테스트만 쓰고, 다음 Task의 테스트는 앞 Task를 커밋한 뒤에 쓴다. 이유: 아직 없는 모듈을 import하는 테스트 파일은 테스트 수집 단계에서 실패하고, 같은 worktree에 커밋하지 않은 채 있으면 앞 Task의 커밋에 섞일 수 있다.
4. **코딩**: coding 세션이 `src/`를 쓴다. 끝나면 test · review 세션에 메시지를 보낸다. 커밋하지 않는다.
5. **커밋 전 리뷰 · 6. 테스트 실행(동시에)**: review 세션은 커밋하지 않은 변경을 리뷰하고, test 세션은 커밋 전 검사(테스트 전체, import 규칙 검사, 린터, 정적 타입 검사, 포매터 검사(포매터를 쓰는 프로젝트))를 실행한다. 통과 기준은 테스트 통과, import 계약 모두 통과, 린터 · 타입 검사 · 포매터 검사 0건이다. 실패와 지적은 coding(또는 test) 세션에 메시지로 보내고, 커밋하지 않고 작업 폴더에서 고친 뒤 5 · 6을 다시 한다. 둘 다 통과하면 coding 세션이 코드와 테스트를 한 커밋으로 만든다. review 세션의 리뷰가 통과하면 coding 세션이 test 세션에 커밋 전 검사를 요청하는 메시지를 보낸다. 지시 문서에는 단계가 끝날 때 누가 어느 세션에 메시지를 보내 다음 단계를 시작시키는지 적는다. 이유: 이것을 적지 않으면 coding 세션은 test 세션의 검사를 기다리고, test 세션은 검사 요청을 받지 못해 커밋이 멈춘다.
7. **결정 기록 · 회고**: 결정은 티켓마다 `<결정 기록 폴더>/<티켓>.md`(ADR) 하나에 쓴다. 티켓의 마지막 커밋 뒤 main이 세션 결과 문서를 보고 `<회고 폴더>/<티켓>.md`에 회고(막힌 것, 반복된 리뷰 지적, 규칙에 더할 것)를 쓴다. 규칙에 넣을 것은 사용자에게 묻는다.

- push와 원격 브랜치 삭제는 사용자에게 묻고, 요청할 때만 한다. PR은 사용자가 만든다.
- 사용자와 정하지 않은 동작에 대한 질문은 design 세션만 main에 보낸다. coding · test 세션은 그런 질문을 design 세션에 보내고, design 세션이 자기 질문과 합쳐 main에 보낸다. main은 design 세션이 보낸 질문만 사용자에게 묻는다. 이유: 세션마다 따로 질문하면 같은 동작을 두 세션이 따로 묻고, 추천이 서로 반대로 나올 수 있다.
- 커밋 단위는 plan의 한 단계 정도로 작게 정한다. 이유: 커밋 전 상태가 길어지면 리뷰와 되돌리기가 어렵다.
- 모듈을 더하거나 옮기거나 역할을 바꾸는 커밋마다 review 세션이 커밋 전 리뷰에서 `<모듈 지도 파일>`(소스 모듈마다 패키지 경로 · 모듈 · 내용 · 쓰는 곳을 적은 표)에 빠진 곳을 지적하고, docs 세션이 그 표를 고친다.
- main은 커밋 보고를 받으면 결과 문서에 커밋 전 리뷰 결과가 있는지 확인하고, 없으면 review 세션에 리뷰했는지 확인한다. 이유: 메시지가 review 세션에 닿지 않으면 커밋 여러 개가 리뷰 없이 만들어진다.
- 작업 흐름을 바꾸면 세션을 띄우기 전에 지시 문서에 넣는다. 이미 띄운 세션에는 main이 그 세션이 다음 작업을 시작하기 전에 멈추라는 메시지를 먼저 보낸다. 이유: 세션은 받은 지시대로 다음 작업을 시작하므로, 바뀐 흐름이 전해지기 전에 이전 방식으로 작업한다. 테스트를 먼저 쓰도록 흐름을 바꾼 뒤 coding 세션이 이전 지시대로 코드를 먼저 고쳐 되돌린 적이 있다.

## 5. 세션 사이 메시지

### 5-1. main 중심 작업 큐(`<작업 큐 폴더>`)

- 사용자는 main과만 대화한다. main이 작업을 지시하고, 다른 세션은 결과를 문서로 남긴다. main 외 세션은 사용자 입력을 기다리는 도구(AskUserQuestion, ExitPlanMode)와 plan 모드를 쓰지 않는다. 이유: 세션이 사람 입력을 기다리는 동안에는 cmux 메시지 전달이 멈추고, 사용자가 세션마다 화면을 확인해야 한다.
- 지시 문서와 결과 문서는 사람이 아니라 Claude 세션이 읽는 문서라 파일 이름 · 제목 · 내용을 모두 영어 Markdown으로 쓴다. 이유: 세션이 읽기 좋은 언어와 형식을 쓴다. 코드 식별자 · 경로 · 사용자 결정 원문(한국어로 정한 문구, 주석 · 문서에 넣을 한국어 문장)은 그대로 둔다. main이 사용자에게 전할 때는 영어 원문을 옮겨 붙이지 않고, 사용자가 읽고 판단하기 좋게 한국어로 다시 쓴다(무엇이 끝났는지, 정할 것과 추천 · 이유, 다음에 일어날 일).
- 지시 문서: main이 `<작업 큐 폴더>/YYYYMMDD-HHMM_<session>_instruction.md`로 쓴다. Role, working directory · branch, user decisions (date), tasks, what to do when done을 쓴다. 지시 문서를 만들기 전에 이 이름 형식을 확인한다.
- 주석 · docstring(무시 주석의 이유 주석 포함)은 승인 표 없이 `문서_주석_양식.md` 규칙대로 쓴다. review 세션이 커밋 전 리뷰에서 규칙 준수를 확인하고, 커밋 뒤 docs 세션이 바뀐 표현을 `<표현 변경 기록 폴더>`에 표로 기록한다. 무엇을 쓸지(동작 · 이유 · 전제)가 코드와 설계로 정해지지 않으면 main을 거쳐 사용자에게 묻는다.
- 메시지 문구(응답 · 로그)를 바꾸는 지시에는 "바뀌는 표현을 표로 사용자에게 보여 주고 승인 → 커밋 → `<표현 변경 기록 폴더>`에 표 기록" 단계를 넣는다. 이유: 지시가 "리뷰 → 커밋"뿐이면 사용자 승인 단계가 빠진다.
- 결과 문서: 세션이 작업을 끝내거나 질문 · 막힘이 생기면 `<작업 큐 폴더>/YYYYMMDD-HHMM_<session>_result.md`로 쓰고, `cmux agent message main "result saved: <path>"` 한 줄을 보낸다. 시각은 저장하는 때다. 읽기만 하는 세션(review · audit)도 결과 문서는 쓴다.
- 결과 문서 형식(main이 그대로 읽고 처리할 수 있게):

  ```markdown
  ---
  session: coding-<티켓>
  instruction: <작업 큐 폴더>/YYYYMMDD-HHMM_coding-<티켓>_instruction.md
  state: done | question | blocked
  branch: <branch>
  commit: <hash if created, otherwise none>
  ---
  ## Done
  - file:line — what changed
  ## Checks
  - command run and result (passed count · failures)
  ## Questions
  - question — options · recommendation · reason ("none" if none)
  ## Next
  - what main should do, or what to send to another session
  ```

- 큐 처리: main은 사용자와의 대화 한 턴을 마칠 때 `<작업 큐 폴더>`의 결과 문서를 이름 순(= 저장 시각 순)으로 읽어 처리한다. 질문이 있으면 사용자에게 묻고, 답을 `<진행 상태 파일>`에 쓰고 세션에 보낸 뒤 그 결과 문서를 지운다. 질문이 없으면 다음 일을 보내고 바로 지운다.
  - 사용자가 "모두 추천대로"처럼 추천을 받아들이는 답을 하면, main은 고른 동작의 조건(적용 대상 · 예외 · 설정 값별 차이)을 문장으로 다시 써서 `<진행 상태 파일>`와 세션에 보내는 메시지에 넣는다. 이유: "모두 추천대로"만 전하면 design 세션이 고른 동작의 범위를 사용자 답보다 넓게 spec에 쓸 수 있다.
- 세션의 작업이 모두 끝나면 main이 그 세션의 지시 문서도 지운다. 모든 작업이 끝나면 `<작업 큐 폴더>`는 비어 있다.

### 5-2. 메시지

- 다른 세션에는 `cmux agent message <surface ref> "<내용>"`으로 보낸다. 받은 메시지는 `cmux agent inbox`로 본다.
- 받는 쪽은 surface ref로 지정한다. surface ref는 `CMUX_QUIET=1 cmux tree`로 확인한다. 이유: `--name` 없이 만든 워크스페이스는 이름이 터미널 제목을 따라 바뀌고, 한 워크스페이스에 세션이 여럿일 수 있다. main은 이름을 `main`으로 고정했으므로 `main`으로 보낸다.
- 답할 때는 `cmux agent message --reply-to <메시지 id> "<내용>"`으로 보낸다.
- `cmux send`(다른 터미널에 글자 입력)는 쓰지 않는다. 이유: 상대 세션이 입력 중이면 그 프롬프트에 섞인다.
- 메시지는 영어로 쓴다(main이 보내는 메시지 포함). 메시지에는 무엇을 했는지, 무엇을 해 달라는지, 관련 파일:줄을 쓴다. 긴 내용(지시, 리뷰 결과 등)은 작업 파일로 쓰고 경로만 보낸다.
- main은 사용자 결정이 필요 없는 일을 먼저 다른 세션에 보낸다. 결정이 필요한 일은 main이 사용자와 진행한다.
- 다른 세션의 메시지를 기다릴 때는 턴을 그냥 끝내지 않는다. 이유: 턴을 끝내고 쉬는 세션은 cmux 메시지가 와도 깨어나지 않는다.
  - Monitor 도구로 60초마다 `cmux agent inbox --surface <자기 surface ref> --state delivered`를 실행하는 반복을 백그라운드에 걸고 턴을 끝낸다. 새 메시지가 나오면 반복이 끝나고 세션이 깨어난다. 이유: 반복은 Claude Code가 로컬에서 실행하므로 기다리는 동안 토큰을 쓰지 않는다.
  - `--surface`를 꼭 준다. 이유: 없으면 모든 세션의 메시지와 자기가 보낸 메시지까지 나온다. main은 `--surface`를 줘도 출력에서 `  main: `으로 시작하는 줄을 빼고 확인한다. 이유: `cmux agent inbox --surface <main>`에는 main이 보낸 메시지도 `delivered`로 보여, 빼지 않으면 main의 반복이 자기가 보낸 메시지로 끝난다.
  - 메시지를 처리하면 `--mark-read`로 읽음 표시를 한다. Stop hook으로 받은 메시지도 `delivered`로 남으므로 처리한 뒤 읽음 표시를 해야 반복이 같은 메시지로 다시 끝나지 않는다. 반복은 메시지 하나마다 끝나므로 계속 기다릴 때는 다시 건다. main은 다시 걸기 전에 이전 Monitor를 TaskStop으로 멈춘다. 이유: 이전 Monitor를 멈추지 않고 다시 걸면 오래된 Monitor들이 만료 알림을 여러 개 보낸다.
  - 커밋을 기다릴 때는 `git rev-parse HEAD`가 바뀔 때까지 확인하는 반복을 쓴다. 이유: 메시지가 늦거나 빠져도 커밋 자체를 본다.
  - 10분 동안 메시지가 없으면 main에 결과 문서("10분째 기다림, 누구의 무엇")를 보내고 계속 기다린다. main은 상대 세션 화면을 보고, 일하는 중이면 그대로 두고, 멈췄거나 확인 창 · 입력 대기에 걸렸으면 사용자에게 알린다. 이유: Task 하나는 1~5분(실측)이지만 큰 구현 · 실제 외부 서비스 실행은 10분을 넘길 수 있어, 10분은 문제가 아니라 확인할 신호다. 사용자 결정을 기다리는 경우는 이 규칙에서 뺀다.

- 네트워크가 끊겼다가 돌아오면 main이 모든 세션의 화면을 확인하고, 멈춘 세션은 사용자에게 알린다. 이유: 턴을 처리하던 세션은 API 오류로 멈추고, Monitor가 만료되면 스스로 깨어나지 못한다.
- main은 지시 문서에 로그 문구 · 키 이름 · 식별자를 적기 전에 코드에서 이름을 확인한다. 이유: 확인하지 않고 적은 로그 키 이름이 코드의 실제 식별자 이름과 달라 지시대로 구현하면 틀린다.
- 측정을 실행하는 동안에는 같은 worktree에서 이력을 바꾸지 않는다(rebase · amend · 체크아웃). 이유: 측정 코드가 그 worktree의 파일을 읽고 쓴다.

## 6. IDE 디버깅

- IDE는 worktree 폴더를 별도 프로젝트로 연다. 인터프리터 · 런타임은 그 worktree의 가상 환경. 실행 설정에 서버가 읽는 설정 파일의 절대경로를 환경변수로 넣는다.
- 디버깅으로 찾은 것은 `cmux agent message <coding의 surface ref> "..."`으로 coding 세션에 보낸다.
- 직접 고칠 때는 coding 세션이 작업하지 않을 때만 고친다. 세션은 마지막으로 읽은 뒤 바뀐 파일을 발견하면 반영할지 묻는다.

## 7. 스킬

- superpowers 스킬을 쓴다. coding 세션은 plan을 실행할 때 `subagent-driven-development` 대신 `executing-plans`를 쓴다. 이유: subagent-driven은 안에서 리뷰 subagent를 따로 만들어 review 세션과 겹친다.
- main 외 세션은 채팅 출력을 영어 caveman(짧게 답하는 모드)으로 쓴다. 세션 사이 메시지와 지시 · 결과 문서는 영어로 쓰되 caveman으로 줄이지 않는다. 파일(코드 · 주석 · 문서 · 커밋 메시지)과 사용자가 읽는 파일(개념 문서 · 회고)은 원래 양식 · 언어(한국어)대로 쓴다. 이유: 사용자는 main과 대화하고, 다른 세션의 채팅은 진행 흐름만 확인한다.
  - caveman을 자동으로 켜는 hook은 환경변수 `CAVEMAN_DEFAULT_MODE`를 설정 파일보다 먼저 읽는다. 기본값은 `~/.config/caveman/config.json`의 `defaultMode` off로 두고, main 외 세션만 띄울 때 `CAVEMAN_DEFAULT_MODE=caveman`을 준다. 이유: 같은 PC에서 main만 끈 채로 둔다.
  - 켜는 상태는 세션 id별로 저장된다. 세션 id 없이 hook을 직접 실행하면 PC 전체에 적용되는 `~/.claude/.caveman-active`가 생기므로, 시험 실행 뒤에는 지운다.
