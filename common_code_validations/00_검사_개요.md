# 00. 검사 개요

- 대상: 서비스를 납품하기 전 · 납품한 뒤에 하는 검사 5가지와, 검사마다 확인하는 모듈
- 언어 · 도구에 매이지 않게 썼다. Python 프로젝트의 명령은 맨 끝 "부록: Python 예"에 있다.

## 1. 검사 5가지

| 문서 | 검사 | 무엇을 확인하나 | 어디서 | 이미지에 들어가나 |
|---|---|---|---|---|
| `01_단위_테스트.md` | 단위 · 통합 테스트 | 함수 · 모듈이 정해진 입력에 정해진 결과 · 오류 코드를 반환하는지(단위), API 요청부터 결과 파일까지(통합). 외부 서비스는 가짜 응답 | 로컬 PC(테스트 러너) | 아니요 |
| `02_정적_검사.md` | 정적 검사 | 실행하지 않고 코드만 읽어 import 방향 · 흔한 버그 패턴 · 타입 오류를 찾음 | 로컬 PC(import 규칙 검사 도구, 린터, 정적 타입 검사 도구) | 아니요 |
| `03_런타임_검사.md` | 런타임 검사 | 서비스가 기동 때와 실행 중에 설정 · 요청 · 외부 응답 · 저장소를 검사해 기동을 실패시키거나, 거부하거나, 실패 · WARNING으로 기록함 | 서비스 안(로컬 · 서버 모두) | 예(서비스 코드 자체) |
| `04_실측_검사.md` | 외부 연동 테스트 · 실측 검사 | 외부 서비스마다 목록과 항목 하나만 받아 보는 외부 연동 테스트, 실제 외부 서비스 전체에 전체 처리를 실행해 건수 · 결과 파일 · 경고를 이전 실행과 비교 | 로컬 PC, 원격 서버 | 아니요(테스트 · 실행 절차) |
| `05_스모크_검사.md` | 스모크 검사 | 새 컨테이너 이미지를 켜서 헬스 체크와 대표 처리 하나가 되는지 짧게 확인 | 로컬 PC(컨테이너 실행 도구) | 아니요(테스트) |

- 런타임 검사만 납품 코드다. 나머지 넷은 납품 전에 사람이 실행하는 테스트 · 절차다.

## 2. 실행 순서

| 순서 | 검사 | 걸리는 시간 | 실패하면 |
|---|---|---|---|
| 1 | 정적 검사(import 규칙, 린터, 정적 타입, 포매터 검사(포매터를 쓰는 프로젝트)) | 수 초 | 코드를 고치고 1부터. import 계약 모두 통과 · 지적 0건이어야 함 |
| 2 | 단위 · 통합 테스트 기본 실행 | 실측해 이 칸에 적는다 | 코드를 고치고 1부터 |
| 3 | 스모크 검사(컨테이너 이미지, 인증 없는 대상 하나) | 빌드 + 대표 처리 1회 | 이미지 정의 파일 · 마운트 확인 |
| 4 | 외부 연동 테스트 | 외부 서비스마다 목록 조회 + 항목 하나 | 외부 서비스 변경인지 코드 문제인지 확인 |
| 5 | 실측 검사 로컬(모든 외부 서비스 전체 처리) | 외부 서비스마다 실측 | 외부 서비스 변경인지 코드 문제인지 확인 |
| 6 | 실측 검사 원격(납품 서버, 사용자) | 로컬과 비슷 | 결과를 문서로 써서 전달 |

- 이유: 빠르고 외부 서비스와 관계없는 검사부터 실행한다. 앞 검사가 실패하면 뒤 검사는 의미가 없다.
- 런타임 검사는 따로 실행하지 않는다. 3 · 5 · 6을 실행하는 동안 동작하고, 결과(기동 실패 · 기동 WARNING, 항목별 오류 코드, 거부 응답, WARNING)를 그 단계에서 확인한다.
- "걸리는 시간" 칸은 실측한 값과 실측 날짜 · 커밋을 적는다. 실측하지 않은 값은 적지 않는다.

## 3. 검사 → 모듈 · 함수

프로젝트마다 이 표를 채운다. 열의 뜻:

| 검사 | 주로 확인하는 모듈 · 함수 | 테스트 · 설정 위치 |
|---|---|---|
| 단위 · 통합 테스트 | 모든 모듈. 테스트 건수가 많은 모듈을 몇 개 적는다 | 단위 · 통합 테스트 폴더와 파일 수, 공통 fixture 파일, 층 사이 공통 도우미 |
| 정적: import 규칙 | 모든 패키지의 import 관계 | 프로젝트 설정 파일의 계약 목록과 계약 수, 계약 테스트 파일 |
| 정적: 린터 · 타입 | 모든 모듈 | 프로젝트 설정 파일의 린터 · 타입 검사 절, 고정한 도구 버전 |
| 런타임: 기동 | 설정 객체, 설정 파일 읽기, 앱 생성(구현이 없는 대상 거부), 기동 처리(임시 파일 삭제, 자격증명 확인, 마치지 못한 작업 확인) | — |
| 런타임: 요청 · 접수 | 요청 검증 모델, 접수 · 거부 검사 함수, 사유 코드 → 상태 코드 표 | — |
| 런타임: 작업 | 목록 검사, heartbeat, 파일 형식 확인, 외부 응답 검증, 날짜 등 부분 값 읽기 | — |
| 외부 연동 테스트 | 외부 연동 모듈마다 목록 조회 · 항목 받기 함수 | 외부 연동 테스트 폴더, 판단 도우미 |
| 실측 | 외부 연동 모듈 전체와 처리 흐름 전체(실행 엔진, 결과 출력, 상태 저장) | 결과 `<실행 기록 폴더>/<날짜>_<티켓>_<대상>/` |
| 스모크 | 이미지 정의 파일, 운영 의존성 목록, 앱 생성 함수, 대표 처리 대상의 연동 모듈 | 스모크 테스트 파일, 결과 `<실행 기록 폴더>/<날짜>_smoke_<대상>/` |

## 4. 결과를 어디서 보나

프로젝트마다 이 표를 채운다. 칸에 들어갈 것:

| 결과 | 위치 |
|---|---|
| 작업 상태 · 작업 오류 | 작업 조회 API와 그 API가 읽는 작업 기록 파일 |
| 항목별 결과 | 작업 폴더의 결과 행 파일(결과, 오류 코드, 비고 열) |
| 로그 전체 | 컨테이너 표준 출력, 구조화 로그(JSON 한 줄씩) |
| ERROR 로그 | 저장 루트 아래 ERROR 전용 로그 파일 |

## 부록: Python 예

| 순서 | 명령 |
|---|---|
| 1 | `uv run lint-imports` · `uv run ruff check src tests` · `uv run pyright` · `uv run ruff format --check src tests`(포매터를 쓰는 프로젝트) |
| 2 | `uv run pytest` |
| 3 | `uv run pytest tests/smoke` |
| 4 | `uv run pytest tests/live` |
| 5 · 6 | `uvicorn`으로 서버 실행 또는 `docker compose up` 뒤 HTTP로 전체 처리 접수(`04_실측_검사.md` 부록) |

- 설정 위치: `pyproject.toml` `[tool.importlinter]` · `[tool.ruff]` · `[tool.pyright]` · `[tool.pytest.ini_options]`.
- 로그 전체: `docker compose logs`.
