# 03. 런타임 검사

- 대상: 실행 중인 서비스가 스스로 하는 검사. 이미지 안 코드에 들어 있고 운영 중에 동작한다.
- 언어 · 도구에 매이지 않게 썼다. Python 프로젝트의 명령 · 출력은 맨 끝 "부록: Python 예"에 있다.

## 1. 런타임 검사란

- 서비스가 실행되는 동안 입력 · 설정 · 외부 응답 · 저장소 상태를 검사해, 잘못된 것을 받으면 정해진 오류 코드로 거부하거나 그 항목 · 작업을 실패로 기록한다.
- 정적 검사 · 단위 테스트와 다른 점
  - 정적 검사 · 단위 테스트는 납품 전에 개발자 PC에서 실행하고 이미지에 들어가지 않는다.
  - 런타임 검사는 납품한 코드 자체다. 운영 중 문제가 생기면 이 검사가 작업 기록 · 결과 행의 오류 코드, HTTP 응답 코드, 로그로 알린다.
- 확인하는 법: 단위 테스트가 거부 경우를 확인한다. 이 문서의 "확인 명령과 예" 절은 로컬 서버나 납품 서버에서 직접 실행해 보는 방법이다.

## 2. 검사 목록

검사마다 번호 · 검사 · 시점 · 모듈 · 함수(파일과 줄) · 실패하면을 표로 적는다. 아래는 HTTP로 작업을 접수해 외부 서비스에서 항목을 받아 저장하는 서비스의 검사 종류다. 프로젝트에 있는 것만 적는다.

| # | 검사 | 시점 | 실패하면 |
|---|---|---|---|
| E1 | 환경변수 형식 · 범위, 빈 경로 · 앞뒤 공백, 로그 레벨 값 | 기동 | 프로세스가 시작되지 않음(설정 검증 오류) |
| E2 | 설정 파일: 모르는 키 거부, 타입 엄격, 중복 키, 이름 형식, 값 사이 규칙(같은 키가 두 목록에 겹침 등) | 기동 | 설정 오류, 프로세스가 시작되지 않음 |
| C1 | 설정 파일의 대상(중지된 대상 포함)마다 구현이 있는지 | 기동(앱을 만들 때) | 설정 오류(구현이 없는 대상 이름을 이름 순으로), 프로세스가 시작되지 않음 |
| E3 | 남은 임시 파일 삭제(저장 폴더 아래) | 기동 | 지우지 못한 파일마다 WARNING, 기동은 계속 |
| C2 | 중지되지 않은 대상의 자격증명 환경변수가 있고 비어 있지 않은지 | 기동 | 역할마다 WARNING(대상 · 역할만, 값 · 환경변수 이름은 쓰지 않음), 기동은 계속 |
| C4 | 대상마다 최근 작업이 실행 중 · 되돌리는 중으로 남았거나 작업 기록이 깨졌는지 | 기동 | WARNING(대상 · 작업 id · 상태), 읽기 실패면 읽기 실패 WARNING. 파일은 바꾸지 않고 기동은 계속 |
| E4 | 헬스 체크: 저장 루트에 시험 파일을 써 봄 | 호출마다(컨테이너 헬스 체크) | 503, 저장소 사용 불가 코드 |
| E5 | API 요청 본문: 필드 타입, 모드 값 목록(엄격) | 요청마다 | 400, 요청 형식 오류 코드 |
| E6 | 접수 검사: 등록되지 않은 대상, 처리 중지, 되돌리는 중, 실행 중, 최근 작업이 끝나지 않음, 동시 실행 대상 수 상한 | 처리 요청 · 재시도 요청마다 | 4xx · 503 거부 코드(HTTP 계층의 사유 코드 → 상태 코드 표) |
| E7 | heartbeat: 작업 기록의 갱신 시각을 일정 주기로 다시 씀 | 작업 실행 중 | WARNING. 갱신 시각으로 멈춘 작업을 찾는 코드가 없으면 그 사실도 적는다 |
| E8 | 목록 검사: 목록이 비었음, 이전보다 크게 줄었음(기준 비율), 비교 키 없음 | 작업마다, 목록을 받은 뒤 | 작업 실패 |
| E9 | 받은 파일 · 만든 파일의 형식(앞 바이트 시그니처) | 항목마다 | 그 항목 행 실패, 파싱 실패 · 렌더 결과 오류 코드 |
| E10 | 작업 실행 시간 상한(모드마다) | 작업마다 | 작업 오류 코드 시간 초과 |
| E11 | ERROR 로그를 파일로: 대상별 파일(날마다 교체), 대상이 없으면 기동 시각 파일 | 늘 | 알림이 없으면 그 사실을 적는다 |
| E12 | 저장한 파일 다시 읽기(엄격): 필드가 없거나 타입이 다르거나 열거형 값이 정해진 값이 아니면 깨진 파일. 모르는 필드는 무시 | 접수 · 작업 시작 · 기동(C4) | 409 마치지 않은 작업 · 503 저장소 사용 불가 |
| E13 | 외부 응답 구조 검증(응답 검증 모델) | 목록 · 항목 응답마다 | WARNING(출처 · 모델 · 위치 · 오류 종류) 뒤 파싱 실패. 목록의 항목 하나만 이상하면 그 항목만 실패 행(비고에 목록 항목 검증 실패), 작업은 부분 성공 |
| E14 | 부분 값(날짜 등) 읽기 | 항목마다 | 값이 있는데 읽지 못하면 빈칸 + WARNING(항목 키 · 필드 · 값), 처리는 계속 |

- 기동 때 순서를 적는다. 예: C1(앱을 만들 때) → E3 → C2 → C4.

## 3. 확인 명령과 예

- 검사마다 직접 실행해 보는 명령과 정상 · 실패 출력을 적는다. 출력은 실제로 실행한 결과만 적고, 실행 날짜를 붙인다. 포트와 작업 id는 실행마다 다르다고 적는다.
- 검사 종류별로 적을 것:

| 검사 | 확인 방법 | 정상 | 실패 |
|---|---|---|---|
| E1 환경변수 | 잘못된 값으로 앱 생성 함수를 실행 | 아무것도 출력하지 않고 끝남 | 설정 검증 오류(필드 이름과 위반 조건) |
| E2 설정 파일 | 같은 명령에서 설정 파일 경로를 확인할 파일로 바꿈 | 아무것도 출력하지 않고 끝남 | 설정 오류(대상과 키, 위반 내용) |
| E4 헬스 체크 | HTTP GET | 200 | 503, 본문 code가 저장소 사용 불가 |
| E5 · E6 요청 · 접수 | 잘못된 모드, 없는 대상, 실행 중 대상, 없는 작업 id로 요청 | — | 400 · 422 · 409 · 404와 본문 `{code, message, detail}` |
| E7 heartbeat | 작업 조회로 갱신 시각을 반복 확인 | 갱신 시각이 주기마다 바뀜 | heartbeat 기록 실패 WARNING |
| E8 · E9 · E10 · E13 · E14 작업 결과 | 작업 조회, 결과 행 파일, 경고 로그 건수 | 작업 성공, 모든 행 성공 | 작업 실패(오류 코드), 실패 행(오류 코드 · 비고) |
| E11 오류 로그 파일 | 로그 폴더 목록과 파일 끝부분 | 파일이 없거나 비어 있음 | ERROR 레코드가 한 줄씩 기록됨 |

- 거부될 때 서버 로그에 기록되는 WARNING 문구(예: `요청 거부 code=… path=…`)도 적는다.
- 거부 코드 → HTTP 상태 표를 이 문서에 옮겨 적는다. 표의 원본은 HTTP 계층의 사유 코드 → 상태 코드 표 하나다. 예:

| 코드 종류 | 상태 | 뜻 |
|---|---|---|
| 등록되지 않은 대상 · 처리 중지 | 422 | 설정 파일에 없는 대상 · 중지 표시된 대상. 구현 없는 대상은 기동이 실패하므로(C1) 요청까지 오지 않음 |
| 이미 실행 중 | 409 | 같은 대상 작업이 실행 중 |
| 마치지 않은 작업 | 409 | 최근 작업이 실행 중 · 되돌리는 중으로 남음(서버가 비정상 종료된 경우) 또는 작업 기록이 깨짐 |
| 동시 실행 상한 도달 | 409 | 실행 중인 대상 수가 설정한 상한에 도달 |
| 되돌리는 중 | 409 | 그 대상을 되돌리는 중 |
| 저장소 사용 불가 | 503 | 저장소 읽기 · 쓰기 실패 |

## 부록: Python 예

pydantic 설정 · FastAPI · uvicorn 서비스에서 확인한 형태다.

```bash
# E1 환경변수: 앱 생성 함수를 직접 실행
ROOT=/tmp/svc-root SITES_CONFIG=$(pwd)/sites.yaml MAX_CONCURRENT=0 \
  uv run python -c "from pkg.main import app_factory; app_factory()"
```

```
pydantic_core._pydantic_core.ValidationError: 1 validation error for Settings
MAX_CONCURRENT
  Input should be greater than 0 [type=greater_than]
```

```
pkg.config.sites.ConfigError: sites.yaml [<대상>]
  - include: Extra inputs are not permitted
```

```bash
# E4 헬스 체크
curl -s -w ' %{http_code}\n' http://127.0.0.1:8000/health
# {"status":"ok"} 200

# E5 · E6 요청 · 접수
curl -s -w ' %{http_code}\n' -X POST http://127.0.0.1:8000/collect \
  -H 'Content-Type: application/json' -d '{"target":"a","mode":"retry"}'
# {"code":"INVALID_REQUEST","message":"[INVALID_REQUEST] 요청 형식이 올바르지 않습니다","detail":{}} 400

# E7 heartbeat
curl -s http://127.0.0.1:8000/executions/<작업 id> | grep updated_at

# 작업 결과 · 경고 건수
curl -s http://127.0.0.1:8000/executions/<작업 id>
grep -c '응답 구조 검증 실패' server.log

# E11 오류 로그 파일
ls <ROOT>/logs/
tail <ROOT>/logs/<대상>/err.log
```

- 설정 검증: pydantic `BaseSettings`(`gt=0`, `le=100` 같은 범위), 설정 파일 모델 `extra="forbid"` · `strict=True`, 중복 키는 YAML 로더를 바꿔 검사.
- 요청 본문 검증 실패는 FastAPI `RequestValidationError` 핸들러에서 400으로 바꾼다.
- 기동 처리는 FastAPI `lifespan`, 컨테이너 헬스 체크는 compose `healthcheck`.
