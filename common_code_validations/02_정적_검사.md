# 02. 정적 검사

- 대상: 코드를 실행하지 않고 소스 파일만 읽어 문제를 찾는 도구 3개(import 규칙 검사 도구, 린터, 정적 타입 검사 도구)
- 언어 · 도구에 매이지 않게 썼다. Python 프로젝트의 설정 · 명령 · 출력은 맨 끝 "부록: Python 예"에 있다.

## 1. 정적 검사란

- 프로그램을 실행하지 않고 코드 글자만 읽어 오류 · 규칙 위반을 찾는다.
- 납품 전 코드 품질 확인용이다. 납품한 이미지에는 들어가지 않고, 운영 중 동작에 영향이 없다.
  - 세 도구 모두 개발 의존성이라 이미지에 설치하는 운영 의존성 목록에 없다.
- 단위 테스트와 다른 점: 테스트는 정해진 입력으로 실행해 결과를 본다. 정적 검사는 실행하지 않으므로 외부 서비스 · 저장소 상태와 관계없이 몇 초 안에 끝나고, 테스트가 지나가지 않는 코드 줄도 읽는다.

## 2. 설정

| 도구 | 하는 일 | 설정에 적을 것 |
|---|---|---|
| import 규칙 검사 도구 | 모듈 사이 import 방향 · 순환 검사 | 계약 목록 |
| 린터 | 문법 오류, 쓰지 않는 import, 흔한 버그 패턴, import 순서 | 줄 길이, 대상 언어 버전, 기본 규칙에 더하는 규칙 |
| 정적 타입 검사 도구 | 타입 표기와 실제 값의 타입이 맞는지, import 순환 | 검사 엄격도, import 순환 보고, 검사 범위(소스 · 테스트) |

- 린터는 그 버전의 기본 규칙에 프로젝트가 필요한 규칙만 더한다. 더하는 규칙과 이유를 설정 옆에 적는다.
- 린터 · 정적 타입 검사 도구 버전은 정확히 고정한다. 이유: 새 버전은 규칙 · 검사를 더한다. 버전을 올리면 설정 파일이 바뀌는 그 커밋에서 새 지적이 함께 드러난다.
- 도구가 처음 실행할 때 다른 런타임을 내려받으면(인터넷 필요) 그 사실을 적는다. 내려받는 곳은 개발 PC뿐이다.

## 3. import 규칙 검사

- 결과는 계약마다 통과 · 위반이다. 하나라도 위반이면 종료 코드가 0이 아니다.
- 위반이면 어느 모듈이 어느 모듈을 import했는지 줄 번호와 함께 출력된다.

### 계약과 관련 모듈

계약마다 이름과 지키는 규칙을 표로 적는다. 계약의 종류:

| 계약 종류 | 지키는 규칙 |
|---|---|
| 계층 | 계층 순서(`<규칙 폴더>/코드_규칙.md`의 계층 그림). 위 계층만 아래를 import |
| HTTP 계층 금지(HTTP API가 있는 프로젝트) | HTTP 계층은 업무 계층을 거쳐서만 저장소 · 외부 연동을 씀 |
| 구현 공통 모듈 금지 | 구현 공통 모듈이 개별 구현을 모름 |
| 진입점만 import | 개별 구현과 구체 저장소 구현은 진입점만 import |
| 응답 모델 사용 범위 | 외부 응답 모델은 외부 연동 모듈만 씀 |
| 형제 독립 | 개별 구현끼리, 응답 모델끼리 서로 import 금지 |
| 한 구현 전용 모듈 | 한 구현만 쓰는 하위 모듈은 그 구현만 import |
| 패키지 안 순환 금지 | 한 패키지 안 모듈끼리 순환 import 금지(함수 안 import, 타입 검사용 import 포함) |

- 계약 검사를 테스트 안에서도 실행하는 테스트를 둔다. 그래서 테스트 기본 실행이 통과하면 계약도 통과한 것이다.
- 계약을 새로 더하거나 고치면, 그 계약이 금지하는 import를 하나 넣은 복사본에서 위반으로 나오는지 확인한다. 이유: 계약이 잘못되어도 통과로 나온다.

### 자주 보이는 지적과 고치는 법

- HTTP API가 있는 프로젝트: HTTP 계층이 저장소 구현을 import함(HTTP 계층 금지 계약 위반)
  - 고치는 법: HTTP 계층에서 저장소를 직접 쓰지 않고 업무 계층에 메서드를 두고 그 메서드를 호출한다.
- 한 패키지 안 두 모듈이 서로 import함(패키지 안 순환 금지 계약 위반)
  - 고치는 법: 함수 안 import로 피하지 않고, 두 모듈이 함께 쓰는 정의를 아래 계층 모듈로 옮긴다. 다른 계층으로 옮기는 것은 사용자에게 묻는다.

## 4. 린터

- 새 프로젝트는 첫 커밋부터 포매터를 쓰고 커밋 전 검사에 넣는다. 포매터 없이 쓴 코드가 있는 저장소에서는 전체에 실행하지 않는다.
  - 이유: 형식만 바뀐 줄이 변경 diff에 섞이는 비용은 포매터 없이 쓴 코드가 있을 때만 생긴다.
  - 포매터 없이 쓴 코드가 있는 저장소에서는 코드를 손으로 정한 줄 길이에 맞춘다.
- 자동 고침은 import 순서처럼 고치는 내용이 분명한 규칙에만 쓰고, 바뀐 줄을 diff로 확인한다.
- 커밋 전마다 0건이어야 한다.

### 자주 보이는 지적과 고치는 법

- import 순서: 알파벳 순서로 바꾼다. import 순서 규칙 하나만 자동 고침으로 고칠 수 있다.
- 예외 처리 밖에서 호출될 수 있는 함수가 "현재 예외 정보 기록" 옵션을 씀: 예외 처리 밖에서 호출되면 트레이스백 없이 기록된다. 인자로 받은 예외 객체를 직접 전달한다.
- 일부러 쓴 코드라 고치지 않을 때: 지적된 줄 끝에 규칙 이름을 적은 무시 주석을 쓰고, 그 줄 위에 이유 주석(개조식)을 쓴다. 예: 항목 하나의 처리 중 예외는 종류와 관계없이 그 항목을 실패 행으로 쓰고 다음 항목으로 진행하는 넓은 예외 처리.

## 5. 정적 타입 검사

- 검사 범위는 소스와 테스트 둘 다다.
- 커밋 전마다 0건이어야 한다.
- 테스트의 지적을 고칠 때: 문자열 리터럴을 열거형으로, 설정 객체 생성을 도우미 한 곳으로 모으고, 가짜 객체는 우리 인터페이스면 그 추상 클래스를 상속하고 라이브러리의 구체 클래스면 타입 단언(cast)으로 넘긴다.
- 운영 코드의 지적을 고칠 때 `assert`나 새 "빈 값이면 예외 발생" 분기를 넣지 않는다. 타입 표기로 고칠 수 없는 곳(라이브러리 반환 타입이 실제보다 넓은 경우 등)은 이유 주석을 단 규칙 이름 무시 주석으로 무시한다.

### 자주 보이는 지적과 고치는 법

- 타입 표기와 실제 값 불일치: 표기를 고친다. 예: 문자열로 표기한 인자에 열거형 값이 들어오면 인자 타입을 열거형으로 바꾼다.
- 빈 값 가능성 접근인데 실제로는 빈 값이 아닌 경우: 라이브러리 타입이 허용하면 타입 단언 · 타입 표기로, 아니면 줄 끝 규칙 이름 무시 주석과 그 줄 위 이유 주석.

## 6. 언제 실행하는가

| 도구 | 시점 | 실패하면 |
|---|---|---|
| import 규칙 검사 | 커밋 전마다 | 커밋하지 않고 고친다. 모든 계약이 통과해야 한다 |
| 린터 | 커밋 전마다 | 0건이어야 한다. 새 지적은 그 지적을 만든 브랜치에서 고친다 |
| 정적 타입 검사 | 커밋 전마다 | 0건이어야 한다. 새 지적은 그 지적을 만든 브랜치에서 고친다 |
| 포매터 검사(포매터를 쓰는 프로젝트) | 커밋 전마다 | 0건이어야 한다 |

## 부록: Python 예

| 역할 | 도구 | 설정 |
|---|---|---|
| import 규칙 검사 | import-linter(`lint-imports`), `import-linter>=2.16` | `pyproject.toml` `[tool.importlinter]` |
| 린터 | ruff, `ruff==0.17.3` | `[tool.ruff]` `line-length = 100`, `target-version = "py312"`, `[tool.ruff.lint]` `extend-select = ["G004", "T20", "B904"]` |
| 정적 타입 검사 | pyright, `pyright==1.1.414` | `[tool.pyright]` `typeCheckingMode = "standard"`, `reportImportCycles = true`, `include = ["src", "tests"]` |

- 더한 ruff 규칙: G004(f-string 로그), T20(`print`), B904(`except` 안 `raise`에 `from` 없음). 줄 길이 초과(E501)는 기본 규칙에 없어 검사하지 않는다.
- PyPI `pyright` 패키지는 처음 실행할 때 Node 빌드를 내려받는다.
- 계약 종류: `type = "layers"`, `"forbidden"`, `"independence"`, `"acyclic_siblings"`. 계약 테스트 `tests/unit/test_import_rules.py`.

```bash
uv run lint-imports
uv run ruff check src tests
uv run ruff check src tests --output-format concise   # 한 줄에 하나
uv run ruff check src tests --statistics              # 규칙별 건수
uv run ruff check src --select I001                   # 규칙 하나
uv run ruff check <파일> --select I --fix             # import 순서 자동 고침
uv run pyright
uv run ruff format --check src tests             # 포매터 검사(포매터를 쓰는 프로젝트)
```

- 출력: `lint-imports`는 계약마다 `KEPT` · `BROKEN`, 끝에 `Contracts: 10 kept, 0 broken.`. ruff 0건은 `All checks passed!`, pyright 0건은 `0 errors, 0 warnings, 0 informations`.
- 위반 예: `pkg.api.routes -> pkg.storage.filesystem`, `No cycles are allowed in pkg.run.` 아래 `- .history -> .manager (1 import)`.
- 포매터: `ruff format`. 커밋 전 검사는 `uv run ruff format --check src tests`.
- LOG014 예:

  ```python
  # 지적: except 밖에서 호출되면 exc_info=True가 트레이스백 없이 기록됨
  logger.error("처리 실패 err_code=%s", info.err_code, exc_info=True)
  # 고친 것: 인자로 받은 예외 객체를 직접 전달
  logger.error("처리 실패 err_code=%s", info.err_code, exc_info=exc)
  ```

- 무시 주석 예:

  ```python
  # 항목 하나의 처리 중 예외는 종류와 관계없이 그 항목을 fail 행으로 쓰고 다음 항목으로 진행
  except Exception as exc:  # noqa: BLE001
  ```

  ```python
  # None 아님: wait_for_selector는 state 기본값("visible")에서 요소 반환 또는 시간 초과 예외 발생
  await field.fill(value)  # pyright: ignore[reportOptionalMemberAccess]
  ```

- 타입 표기 불일치 예:

  ```python
  # 지적: Argument of type "str" cannot be assigned to parameter "mode" of type "Mode"
  async def _open(self, key: str, mode: str, ...)
  # 고친 것
  async def _open(self, key: str, mode: Mode, ...)
  ```
